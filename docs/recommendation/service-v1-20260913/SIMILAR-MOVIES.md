# 영화 상세의 비슷한 영화 — 저비용 v1

상태: **APPROVED — 사용자 요청에 따른 로컬 설계 기준** · 2026-09-13.
새 모델 학습·인덱스 구축·팀 API/DB 수정·실제 품질 검증은 아직 실행하지 않았다.
[전체 설계](README.md), [GKT 전처리](GROUPS.md), [실행 기본값](similar-movies.v1.json)을 함께 따른다.

**기존 장르·키워드·줄거리 벡터를 재사용한다. Spring이 pgvector HNSW로 가까운 영화를 찾고
영화별 상위50편을 공용 캐시에 저장한다. 상세 화면은 기본10편을 가로 목록으로 보여준다.**
화면 폭에 따라 처음5편 정도가 보여도 추가 모델 호출 없이 나머지를 탐색한다.
맞춤2+발견1과 독립된 상세 탐색 기능이며 GBT/FM/ALS 학습 완료를 기다리지 않는다.

## 1. 선택한 방법과 비용

DB 근접 검색1회를 수행한다. 새 GPU·벡터 DB 서비스·Faiss 의존성을 추가하지 않는다.
로컬에서 벡터·검증 예제·예열 결과를 준비할 수 있으나 HNSW 인덱스는 대상 PostgreSQL에서
구축한다. 벡터 파일 복사만으로 서버 인덱스까지 설치됐다고 보지 않는다.

기준237,817편의131개 float32 원소는 약124.6MB다. 이는 단순 배열 산술이며 PostgreSQL 행,
인덱스, 메타데이터, 캐시, 작업 메모리는 추가다. 실제 크기·구축 시간·응답 시간은 측정한다.
전체 영화 쌍의 유사도 행렬이나237,817편×50편의 이웃을 미리 전량 생성하는 것을 시작 조건으로 삼지 않는다.

## 2. 영화 벡터와 유사도의 의미

GROUPS §2의 고정 전처리를 그대로 transform해서 만든 `content_x`를 사용한다.
전처리와 벡터의 source hash·export만 재사용하며 상위/하위 중심·그룹 대표·할당·과거 router는
이 기능의 실행 입력이 아니다. 따라서 전체 그룹 bundle 준비와 유사 영화 준비 상태를 분리한다.

```text
content_x = L2(concat(sqrt(0.50) × 장르19,
                     sqrt(0.35) × 키워드64,
                     sqrt(0.15) × 줄거리48))
```

각 블록의 전처리·결측·L2 규칙은 GROUPS와 같다. 비중은 기존 벡터의 재사용 값이며,
상세 유사 영화 품질에 최적이라고 실험으로 증명한 값은 아니다. 원본 float64 벡터·그룹 배정은
변경하지 않는다. DB용으로 float32 사본을 만들고 유한값·차원·norm을 검증한다.
`sub_supported=true`가 필요하지만 `top_supported`나 `group_mapped`는 필요하지 않다.
따라서 장르가 없어도 키워드/줄거리로 유효한 벡터가 있으면 검색할 수 있다.

이 경로의 점수는 **DB float32 사본 사이의 cosine**으로 정의한다.
`similarity = 1 - (embedding <=> base_embedding)`이며 부동소수점 범위 초과만[-1,1]로 자른다.
유효한 양의 점수만 결과로 사용한다. 원본 float64 cosine과 절대차≤1e-6인지 export 검수한다.
GROUPS의1e-10/할당 일치 기준을 DB 사본에 적용하거나 원본 벡터를 사본으로 덮어쓰지 않는다.

유사도는 예상 별점·만족 확률이 아니다. TMDB 평점·KOBIS 관객·ALS 점수를 더하지 않는다.
대중 지표는 후보 자격에만 사용하고 유사도 순서를 인기순으로 바꾸지 않는다.
K-means 소속, 발견10×10, 사용자 pool500은 이 검색의 제한 조건이 아니다.

## 3. 기준 영화, 후보, 로그인 처리

| 구분 | 규칙 |
| --- | --- |
| 기준 영화 | 서비스 ID와 상세 조회 권한이 유효하면 대상. 낮은 인기/관객 수 때문에 탐색을 막지 않음. 벡터가 없거나0이면200 빈 목록 |
| 추천 후보 | POLICY §2의 활성·개봉·성인/비디오 false·표시정보·`T_ok OR K_ok`, 검증된 ID 연결, 유효한 content 벡터 필요 |
| 자기 자신·중복 | 같은 serviceMovieId 및 같은 검증된 TMDB ID의 기준 영화 제외. ID 충돌은 게시 전 오류이며 제목만으로 다른 영화를 합치지 않음 |
| 비회원 | 공용 결과에 현재 후보 자격을 적용. 취향·K·온보딩 입력 불필요 |
| 로그인 | 같은 공용 순서에서 현재 확정 감상·현재 실제 별점·관심없음 영화를 제외. 사용자별 점수 재계산은 하지 않음 |
| 세션·구독 | 맞춤/발견에서 이미 노출된 사실만으로 상세 이웃을 제외하지 않음. API에 없는 취향/OTT 필터를 몰래 적용하지 않음 |

로그인 감상·관심없음 제외는 팀 문서의 미정 항목에 대한 **이번 로컬 v1 기본 선택**이다.
공용 캐시에 사용자 제외 결과를 저장하지 않는다. 캐시 후의 일괄 DB 조회에서 최신 공개 상태와
최신 사용자 제외를 함께 검사하며, 로그인 상태 확인에 실패하면 익명 결과로 조용히 바꾸지 않는다.
구독 OTT는 기존 상세/카드 표시 계약을 따르며 유사도에 넣지 않는다.

출력 목표는10편이고 API 호환 범위는 `size=1..20`, 기본10이다. 상세 UI는10을 요청한다.
확보된 결과가5~9편이면 그대로,1~4편이면 그만큼,0이면 빈 안내를 보여준다.
개수 때문에 무관한 인기 영화나 비적격 영화를 채우지 않는다.50편에서 제외 후 부족해도
요청 중 추가 검색을 반복하지 않는다. ANN과 필터 때문에 전역에는 적격 이웃이 있어도 짧아질 수 있으며 이를 측정한다.

## 4. 벡터 준비와 검색 절차

1. 검증된 서비스ID↔TMDB 연결, GKT 전처리 버전, 콘텐츠·후보 자격 스냅샷을 고정한다.
   KOBIS 미확정 자료를 사용하지 않으며 TMDB만 자격을 충족한 후보도 정상 지원한다.
2. 모든 상세 조회 대상의 지원 벡터를 저장하고, 후보 적격성은 별도 boolean으로 보관한다.
   기준 영화가 후보 하한 미달이어도 query 벡터는 읽을 수 있어야 한다.
3. 버전별 PostgreSQL 파티션에 `vector(131)`를 적재하고 후보 적격 행만의 partial HNSW
   `vector_cosine_ops` 인덱스를 만든다. 다른 버전의 벡터가 같은 근접 탐색에 섞이지 않게 한다.
4. 캐시 미스에서 읽은 버전을 요청 끝까지 고정한다. 안쪽 SQL은 해당 버전·후보 적격 predicate와
   `ORDER BY embedding <=> :base ASC LIMIT 100`을 사용한다. 바깥 단계에서 자기 자신·중복·
   비양수 점수를 제거하고 `similarity DESC, serviceMovieId ASC`로 정렬해 최대50편을 남긴다.
5. 계산 성공한 공용 목록만 캐시에 기록한다. 이후 사용자와 현재 공개 상태 필터를 적용해 size만큼 반환한다.

100은 반환 후보 수 상한이며 탐색한 노드 수나 총 계산량 상한이 아니다. 트랜잭션 안에서
`hnsw.ef_search=200`, `statement_timeout=500ms`를 설정하고 종료 시 설정이 커넥션 풀에 남지 않게 한다.
인덱스 초기값은 `m=16`, `ef_construction=64`다. 지원 버전에서는 iterative scan을 `off`로 명시한다.
미지원 버전에 해당 설정을 보내지 않으며 확장 버전과 적용된 설정을 manifest에 기록한다.
SQL 계획·전체 API1,000ms 제한도 검수한다. 이 값은 운영 예산이며 측정된 지연 보장이 아니다.

`ORDER BY 1-distance DESC`만으로 인덱스 검색을 요청하지 않는다. partial predicate/버전 파티션을
실제 쿼리에서 사용해 인덱스가 선택되는지 EXPLAIN으로 확인한다. 작은 카탈로그의 planner
선택도 기록하며 큰 카탈로그에서 무제한 전수 검색으로 퇴행하는 상태로 게시하지 않는다.
동일 후보 집합의 점수·ID 정렬은 안정적이어야 하지만 HNSW가 전역 정확 Top10을 보장하지는 않는다.
표현·벡터가 동일한 영화가 많을 때도 ANN이 반환하지 않은 동률 ID까지 전역 순서를 보장한다고 하지 않는다.

캐시 생성은 Spring 인스턴스당 최대2개 동시 실행, 대기 최대50ms, 재시도0회다.
동일 인스턴스의 같은 키 요청은 진행 중 계산을 공유한다. 여러 인스턴스의 동일 키 중복 계산은
허용하되 동일 버전의 완성 목록만 원자적으로 저장한다. 총 DB 동시성은 인스턴스 수를 곱해 검수한다.
무제한 비동기 작업을 쌓거나 캐시 미스마다 Spark/Consumer 작업을 시작하지 않는다.

## 5. 저장·캐시·버전 교체

아래 명칭은 구현할 로컬 논리 계약이다. 현재 팀 DB에 테이블/인덱스가 있다는 뜻이 아니다.

| 산출물 | 필수 내용 |
| --- | --- |
| `similarity-manifest.json` | similarityVersion, 최초 생성 sourceCatalogVersion, eligibilityVersion, ID매핑/export SHA, GKT 전처리/벡터 SHA, 이 recipe SHA, 원본/DB precision, PG/pgvector 버전, index 설정·검수, 벡터/후보 수, 준비 상태 |
| `movie_content_vectors_gkt131` | 버전별 파티션; `(similarityVersion, serviceMovieId)` 고유, tmdbId, vector(131), sourceHash, candidateEligible. 한 버전의 tmdbId 연결도 유일성 검사 |
| 버전 등록 정보 | 검증된 manifest와 물리 파티션/인덱스 연결, 단일 활성 similarityVersion, 이전 정상 버전. PostgreSQL 등록 정보가 활성 버전의 기준이며 트랜잭션으로 전환 |
| 공용 Redis 캐시 | `feelm:v1:similar:{similarityVersion}:{serviceMovieId}`, 최대50개 `{movieId, similarity}`와 base ID·version·완료 시각. 정상 TTL24시간, 사용자·표시 문구·개인 상태 미저장 |
| 선택적 예열 파일 | 같은 버전의 성공한 공용 이웃 목록과 SHA. Spring과 같은 검색·정렬로 생성한 결과만 import |

`similarityVersion`은 불변이며 유사 검색용 콘텐츠·후보 적격 집합/flag·매핑·recipe 중 하나라도
바뀌면 새 버전이다. 전체 catalogVersion이 TMDB 투표 수 등의 갱신으로 바뀌어도 위 입력 해시가
모두 같으면 기존 인덱스·similarityVersion을 재사용한다. manifest의 sourceCatalogVersion은
최초 생성 출처로 보존하고 새 원천을 사용해 다시 계산한 것처럼 덮어쓰지 않는다. 원천 값 변화로
후보 하한 통과 여부가 달라지면 eligibilityVersion과 similarityVersion은 반드시 바뀐다.
빈 목록도 지원 여부·버전과 함께 성공 응답으로 캐시할 수 있다.404·타임아웃·실패를 정상 빈 캐시로 저장하지 않는다.
Redis 실패 시에도 동시성 제한 안에서 DB1회 조회는 가능하다. DB도 실패하면503을 반환한다.
다른 버전의 캐시를 현재 결과처럼 읽지 않는다.

벡터·후보 자격이 같은 날에는 기존 버전을 재사용한다. 변경 시 새 벡터/인덱스·검수를 준비하고
활성 버전을 원자적으로 교체한다. 후보 영화 하나의 벡터가 바뀌어도 여러 기준 영화의 이웃이
달라질 수 있으므로 변경 영화의 키만 삭제하지 않는다. 새 버전 키 공간으로 전환한다.
이전 버전의 요청·인덱스는 진행 요청이 끝날 때까지 보존하고 rollback 대상으로 유지한다.
삭제·비공개·현재 부적격 영화는 캐시나 이전 버전이 남아 있어도 반환 직전 차단한다.

예열은 선택사항이며 배치당 최대1,000개 기준 영화를 한 작업에서 순차 처리한다.
유효 TMDB vote_count DESC/null last, serviceMovieId ASC로 선택하고 벡터 지원 영화만 사용한다.
이는 캐시를 먼저 채울 순서일 뿐 추천 순위나 카탈로그 검색 범위를 바꾸지 않는다.
나머지는 첫 요청에서 준비한다. 새 기준 영화가 아직 게시 벡터에 없으면200 빈 목록이며,
온라인에서 TMDB 조회·텍스트 임베딩 생성을 추가하지 않는다.

## 6. 기존 API·화면·이벤트와 연결

로컬 팀 HEAD `b622d5e`(origin/develop보다8커밋 뒤)의 API-031/FR-11을 확인했다.
현행 공개 계약은 `GET /api/v1/movies/{movieId}/similar?size=10`, 인증 선택, size 기본10·최대20이다.
`baseMovieId`, `items[].movieId/title/posterUrl/releaseYear/averageRating/similarity/reason`을 유지한다.
size 비정수·범위 밖은 공통400 검증 오류로 처리한다. 미존재/조회 불가 기준 영화404,
검색 시스템 미준비·실패·시간 예산 초과는503이며, 정상 조회의 벡터 미지원·이웃 부족은200이다.
오류 코드는 기존 `RESOURCE_NOT_FOUND`/`RECOMMENDATION_UNAVAILABLE`을 사용한다.

`averageRating`은 기존 서비스 별점 집계다. TMDB 평균을 대신 채우거나 similarity를 별점으로 표시하지 않는다.
`reason.summary`는 원본 정보의 공통 장르가 있으면 `스릴러 장르가 비슷해요`처럼 고정 템플릿으로 만든다.
`factors`에는 실제 공통 장르만 `GENRE`로 넣는다. 공통 장르가 없으면 `영화 콘텐츠 정보가 비슷해요`,
factors=[]로 표시한다. 특정 블록이 존재한다는 이유만으로 그 블록이 양의 유사도에 기여했다고
단정하지 않으며 감독·배우·결말을 추론하지 않는다.
이유 문구/장르명은 반환할 최대20편에만 현재 영화 메타데이터로 조립하며 LLM을 호출하지 않는다.

상세 API와 유사 API는 분리 호출한다. 유사 기능503/빈 목록이 영화 상세·리뷰·평가를 막지 않는다.
현재 프런트는 유사 목록 mock이며 별도 빈 안내가 있다. 실제 조회로 교체하고 오류/빈 상태는 구분해서 표시한다.
반환한 카드를 누르면 목적 영화의 일반 상세로 이동한다. 가짜 recommendationItemId를 만들거나
기준 영화의 추천 항목 ID를 목적 영화에 전달하지 않는다. 이 목록은2+1 세트·예약·추천 이력·
recommendation_items·노출 제외 세션·inputVersion을 생성/소비하지 않는다.
목록 조회/캐시 미스는 감상·평점·VIEW가 아니다. 카드 클릭 후 정상 상세 조회의 기존 로그인 VIEW만
해당 계약대로 처리하며 추천 항목 ID가 필요한 RECOMMENDATION_CLICK을 만들지 않는다.
익명 이용자에 가짜 userId를 부여하지 않는다.

팀 문서는 E5 계열 다국어 임베딩을 잠정 기준으로 둔다(ADR0014). 이 로컬 v1은 비용을 위해
GKT131을 재사용하는 **표현 변경안**이다. API-031·ADR0014·DB 차원/버전·SecurityConfig의 선택 인증,
Spring loader/query/cache·프런트 mock 교체가 이행 대상이다. 폐기된 IN-04 FastAPI 경로는 되살리지 않는다.
팀 파일·GitLab·Notion은 이번 작성에서 수정하지 않았다.

S07은 seed339로 최대200개 기준 영화를 결과를 보기 전에 고정한다. 한국/그 외,2020년 이후/이전,
TMDB만/KOBIS만/둘 다, 장르만/복합 정보/장르 결측의 표본 수와 중복 제거 절차를 먼저 기록한다.
정확 대조는 같은 후보 자격·DB float32 벡터의 전역 cosine Top10을 **표본 기준 영화에만** 계산한다.
ANN과 정확 대조 모두 자기 자신/같은 TMDB 제외·ID 중복 제거·양의 점수 조건을 동일하게 적용한다.
이 공용 검색 검수에는 사용자 감상/관심없음 후처리를 넣지 않는다. ANN 결과도 정렬된 최종
공용 목록의 **첫10편만** 사용하며 검색 후보100편이나 캐시50편 전체를 정답과 비교하지 않는다.
동률 경계는 정확10위 점수와 동률인 영화를 정답 집합에 포함해 같은 점수의 ID 선택을 실패로 세지 않는다.
분모는 min(10, 자기 자신을 제외한 실제 양의 유사도 적격 고유 영화 수);0이면 N/A다.
분자는 ANN 첫10편과 동률 경계를 확장한 정확 정답 집합의 교집합 크기다. 각 기준 영화의
복원율=분자/분모이며 N/A를 제외한 영화 동일 가중 평균을 사용한다. 표본/분모/동률 수를 함께 보고한다.
`정확 Top10 복원율` 평균≥0.95를 검색 구현의 시작 검수 목표로 두며, 이 수치는 추천 만족도가 아니다.
실패하면 배포 준비 미완료로 남기고 검색 설정을 검토한다. 결과를 보고 무제한 검색으로 바꾸지 않는다.

별도로 고정한 최대30개 사례의 첫5/10편을 사람이 검토해 주제·설정·장르의 관련성, 설명 오류,
장르만 같고 내용은 다른 사례, 프랜차이즈 집중을 기록한다. 빈/부족 비율과 소수 국적·신작의 지원도 함께 본다.
MovieLens MSE나 기존 GBT 승패로 영화 간 유사 품질을 대신하지 않는다. 품질 검토 전에는
이 기능의 유사성·한국 사용자 만족도가 검증됐다고 발표하지 않는다.
