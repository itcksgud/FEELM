# 서비스 추천 v1 — 운영 순서

상태: **APPROVED — 사용자 확정 제품 결정을 반영한 로컬 구현 기준.**  
팀의 공통 API·DB·Redis 계약 승인, 코드 반영, 병합·배포 완료를 뜻하지 않는다. 작성 2026-09-13.

정책과 모델의 기준은 [POLICY](POLICY.md), [MODELS](MODELS.md)이며, 데이터 형식·이행·검증은
[CONTRACTS](CONTRACTS.md)를 따른다. 과거 `service-final-20260913`의 ALS 자동 혼합·유형별2편·그룹25 정책을 사용하지 않는다.
KOBIS의 원행·신원 제안·검토된 매핑·서비스 snapshot 경계는 [KOBIS 데이터](KOBIS-DATA.md)를 함께 따른다.

## 1. 역할과 계산 시점

**배치는 맞춤 후보를 만들고, 사용자 입력이 바뀌면 그 후보 전체를 최신 특징으로 다시 정렬한다. 기본 모델은 GBT다.**
FM·ALS는 같은 후보와 평가 조건을 비교하기 위한 별도 모델 경로이며 기본값을 자동으로 대체하거나 섞지 않는다.
ALS+GBT·ALS+FM의 전환/혼합도 [결합 비교 명세](HYBRID-COMPARISONS.md)에 따라 shadow로
계산한다. component 점수를 한 번씩 구해 재사용하며 오류·정상 미지원·실제 ALS 기여를
별도 기록한다. 기본 응답은 GBT이며 이 비교 결과로 노출 모델을 자동 변경하지 않는다.

| 담당 | 해야 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| Spark Batch 후보 Producer | 영화·T/K 특징 스냅샷, 고정 군집 배정, 그룹별 사전 순위, 사용자 맞춤 후보 최대500 생성 | 사용자 API 요청 안에서 전체 카탈로그 점수 계산 |
| Python 추천 Consumer | 최신 입력/반응 특징, 맞춤≤500·발견≤100 전부 정렬·게시 | 맞춤20/발견10으로 미리 잘라 교차 중복 대체 후보를 잃는 것, GBT 나무 재학습 |
| Spring | 평가·감상·관심없음 저장, Outbox, 입력 버전, 최종 제외, 맞춤2+발견1 세트·노출 이력 | GBT/ALS 추론을 Java에 중복 구현 |
| Spark Streaming | 앱 조회·클릭 등 여러 사용자 행동과 전역 추세 집계 | 개인 모델 학습·개인 전체 후보 재생성 |
| PostgreSQL | 실제 사용자 입력·계정 상태·추천 이력의 원본 | 외부 원천값을 서비스 사용자의 별점으로 저장 |
| Redis | 완성된 후보·순위 묶음의 캐시와 활성 포인터 | 유일한 입력 버전 원본, UUID의 크기 비교 |

T는 TMDB, K는 KOBIS 출처다. 개인화 전환의 `K=10편`과 혼동하지 않도록 코드에서는
`personalization_min_ratings`와 `kobis_*`처럼 서로 다른 이름을 사용한다.

## 2. 고정 운영값

| 항목 | v1 값 |
| --- | --- |
| 실제 별점 | 0.5~5.0, 0.5단위 보존 |
| 개인화 전환 / 모델 입력 | 서로 다른 실제 평가10편 / 최신 원본10편. 상세 정렬·온보딩 규칙은 POLICY |

| 맞춤 배치 후보 / 실시간 점수화 | 최대500 / 중간 Top100 절단 없이 현재 후보 전부 |

| 발견 상한 준수 | 11번째그룹·같은그룹11번째영화로 부족분을 채우지 않음 |

| 대중 근거 하한 | 유효 TMDB평균+투표≥21 또는 검증된 동일누적 KOBIS관객≥10,000 |
| 하한 적용 범위 | 추천 후보만. 검색·실제평가·감상·최신10편 선택에는 적용하지 않음 |
| 정기 배치 | 매일06:00 KST를 운영 기본값으로 설정. 통계적 최적 주기라는 뜻은 아님 |

두 출처가 모두 하한에 못 미치는 영화는 추천 후보에서 제외한다. 콘텐츠 보충으로 다시 넣지 않는다.
한 출처만 통과하면 그 출처만 후보 순위에 기여한다. 실제 유효 원천값은 사용자 이력 특징에 남긴다.
관객 수가 적은 영화를 좋아한 반응 자체를 없애거나 미매칭 관객 수를0으로 취급하지 않는다.

## 3. 첫 배치와 서비스 시작

1. 서비스 DB의 movie ID↔TMDB export와 검토된 TMDB↔KOBIS 매핑, 원천·통계 기준일·수집 시각·대상기간·누적범위·결측 상태를 검증한다. 원행 staging/신원 제안은 확정 매핑과 분리한다.
2. 고정 전처리·8맛/하위그룹 중심과 할당을 로드한다. 목록 변경만으로 중심을 다시 학습하지 않는다.
3. raw source validity와 추천 후보 eligibility를 별도 계산하고 T/K 그룹별 순위 및 공용 초기 후보 최대500을 만든다.
4. 모델 manifest의 모델 종류·특징 개수/순서·보정·원천 버전을 검사한다. v1 KOBIS245와 legacy RH230을 섞지 않는다.
5. 사용자 상태에 맞는 POLICY 경로로 전체 적격 카탈로그를 정렬해 pool500을 만든다. K≥10이고 모델/이력이 준비됐으면 GBT, K<10이면 초기 콘텐츠/대중 경로다. 생성 당시 입력 버전과 rankingMode를 기록한다.
6. 모든 산출물의 ID·중복·유한값·용량·해시와 매핑 검토 근거, 선언한 cutoff/누적범위를 검증한 뒤 하나의 bundle로 공개한다. 후보·이력 특징은 같은 정규화 source를 읽어야 한다. 일부 파일만 성공한 버전은 게시하지 않는다.
7. Consumer가 같은 bundle의 후보와 특징을 읽어 최초 순위를 만든다. Spring은 현재 입력 버전과 맞는 결과만 세트로 사용한다.

**현재 목표인 KOBIS245 GBT 학습 산출물은 아직 준비되지 않았다(`buildStatus=NOT_BUILT`).** 이전230 모델에 열15개를 덧붙이거나
부족한 값을0으로 채워 v1 모델 준비 완료로 표시하지 않는다. 학습·parity·평가 게이트는 MODELS가 정의한다.
모델 미준비 상태에서는 POLICY의 초기 콘텐츠/대중 경로로 동작할 수 있으나 `modelReadiness=NOT_READY`와
실제 경로를 기록한다. 그것을 GBT 추천 성능이나 GBT 서비스 가동으로 보고하지 않는다.

확장 KOBIS 수집은2004~2025년과2026-09-12까지의 전체 관측72,700행을 보존하고 독립 검토를 마쳤다.
직접 코드는 연도별 처음100행에서만 확인했으며2,300행·고유2,176코드다. 코드 없는70,400행과
KOBIS/TMDB 신원 제안은 고유 영화나 서비스 확정 매핑으로 사용하지 않는다. 현재 교차 원천 확정 ID는0건이다.
따라서 수집/연결 검토 PASS만으로 첫 서비스 bundle의 K 유효성 또는 KOBIS245 준비 게이트를 통과시키지 않는다.

## 4. 강한 입력 변경 뒤 실시간 반영

1. Spring은 실제 별점·온보딩·확정 감상 추가/삭제·추천 필터의 변경과 `inputVersion` 증가, 현재 미소비 세트 무효화/예약 해제, Outbox 저장을 같은 트랜잭션에서 처리한다. 실제 세션 노출 이력은 보존한다.
2. Kafka Consumer는 event payload의 과거 값 대신 최신 DB 이력을 읽고 최신 원본10편 및 반응 특징을 만든다.
3. 동일 bundle의 기존 맞춤 pool이 있으면 **영화 ID 집합만** 재사용한다. 후보500 모두에 현재 입력으로 새 점수를 계산한다.
4. 발견은 전체 실제 감상 이력으로 적격 그룹을 정하고, 최신 사용자 프로필로 그룹 순서를 계산한다.
5. 공급이 있는 그룹 최대10개에서 T/K 순위로 각각 최대10편을 고른다. 확보한 후보 전부를 현재 경로의 점수로 정렬한다. Consumer는 맞춤≤500·발견≤100 전체를 게시하고 Spring이 라운드별로 조립한다.
6. 점수화가 끝나면 입력·계정 상태와 bundle을 다시 검사한다. 오래된 작업이 새 입력의 결과를 덮어쓰지 못하게 한다.
7. 새로운 `rankingVersion`을 게시한다. 기록한 `rankingInputVersion`은 계산에 실제 사용한 최신 입력 버전이다.
8. 동시에 최신 입력용 맞춤 후보 재생성을 targeted Spark job으로 요청한다. 같은 사용자 변경은 최신 상태로 합칠 수 있다.

GBT 나무와 모델 보정값은 이 과정에서 바뀌지 않는다. 바뀌는 것은 사용자 반응 특징과 후보별 예측값이다.
ALS 비교 모드라면 Factor가 있는 입력의 Fold-in을 다시 계산하지만, ALS 미지원 영화를 GBT 기본점수로 위장하지 않는다.

확정 감상만 추가하거나 삭제해도 발견의 viewed 분자·분모와 그룹 자격이 달라진다. 별점이 같다는 이유로 이전 순위를 유지하지 않는다.
평점 등록과 파생 감상 전환이 같은 트랜잭션에서 일어나면 inputVersion은 한 번만 증가시킨다.
같은 값을 다시 저장한 요청은 변화가 아니며 중복 이벤트로 버전을 추가 증가시키지 않는다.
관심없음은 최종 제외와 현재 라운드 revision만 바꾼다. 세션 노출·일반 클릭은 별점·확정 감상·inputVersion을 증가시키지 않는다.

### 배치 후보가 이전 입력으로 만들어졌다면

| 필드 | 의미 |
| --- | --- |
| `builtFromInputVersion` | 배치가 pool의 영화 ID를 골랐을 때 사용한 사용자 입력 |
| `rankingInputVersion` | 현재 Consumer가 후보를 재정렬할 때 사용한 사용자 입력 |
| `candidateRefreshPending` | pool이 이전 입력으로 만들어져 새 후보 준비를 기다리는지 여부 |
| `provisionalPool` | 개인 pool이 없어 공용 T/K500을 임시 사용했는지 여부 |

예를 들어 pool은 입력7에서 만들었어도 입력9의 특징으로500편을 다시 점수화하면 즉시 취향 변화를 반영할 수 있다.
다만 입력9에 맞는 새 영화가 기존500 밖에 있을 수 있으므로 `candidateRefreshPending=true`를 기록하고 targeted 재생성을 한다.
이 임시 허용은 **후보 집합에만** 적용한다. 입력7의 과거 점수를 입력9의 점수로 제공하지 않는다.

## 5. 신규 사용자·pool 누락·targeted 후보 작업

| 상황 | 즉시 사용할 경로 | 비동기 후속 |
| --- | --- | --- |
| 개인 pool 없음, K<10 | 같은 bundle의 배치 공용 T/K500에서 초기 콘텐츠/대중 경로 | 현재 사용자에 대한 targeted pool 준비 |
| 개인 pool 없음, K≥10, 모델 준비됨 | 같은 공용500에 현재 GBT 특징·점수 적용, provisional 표시 | 현재 입력 기반 개인 pool 준비 |
| 기존 pool은 있지만 입력이 새로 바뀜 | 기존 membership500을 최신 입력으로 재정렬 | 최신 입력에 맞춘 pool 재생성 |
| 맞춤 pool 소진 | 공용/이전순위도 현재 제외를 적용해 가능한 경우만 제공 | POOL_EXHAUSTED 작업이 현재session의노출·활성예약을전체카탈로그검색에서제외해다음500 생성 |
| 맞는 bundle의 pool도 공용 pool도 없음 | 추천 준비/이용불가 상태 | bundle/pool 복구. API 요청 안에서 전체 영화 계산 금지 |

targeted 작업은 정기 배치와 **같은 후보 Producer 코드**를 사용자 범위만 줄여 실행한다.
K<10 targeted 작업도 전체 적격 카탈로그를 초기 콘텐츠 방향 또는 T/K 대중 순서로 정렬해500편을 만든다.
단지 targeted job이라는 이유로 GBT 경로를 강제하지 않는다. 모델/이력 미지원의 초기 경로도 POLICY와 같은 판정을 사용한다.
각 요청은 불변 `jobId`, `desiredJobToken`, `expectedBasePoolVersion`, 대상 입력 버전을 가진다.
재시도는 같은 ID를 재사용한다. 같은 입력 버전에서 재빌드가 겹쳐도 최신 token과 기대 pool이 맞는 작업만 게시한다.
입력이 더 바뀌었으면 오래된 결과를 폐기하고 최신 입력 작업을 준비한다. 새 pool 게시 후 Consumer 재정렬을 다시 요청한다.
재시도 도중 입력이나 bundle이 달라졌다면 같은 불변 version에 새 내용을 쓰지 않는다. 기존 작업을 대체된 상태로 끝내고
새 입력을 대상으로 새 job/version을 만든다. 단순 전송 재시도와 새 입력의 재계산은 서로 다른 작업이다.

pool 생성과 ranking 재정렬은 동시에 진행할 수 있으므로 원하는 작업 상태도 `desired-job:pool`과
`desired-job:ranking`으로 나눈다. ranking 작업은 자신의 desiredJobToken, expectedRankingVersion,
대상 pool/input/bundle/session을 비교해 게시한다. 같은 입력·pool의 두 재정렬도 나중에 끝난 오래된 작업이 최신 ranking을 덮어쓰지 못한다.
pool 게시 뒤 새 ranking 요청은 ranking 상태만 갱신하며 진행 중인 pool 작업 token을 덮어쓰지 않는다.

### 소진 때 같은500편을 반복하지 않기

일별 일반 pool은 세션 노출을 영구 제외하지 않는다. 대신 **triggerReason=POOL_EXHAUSTED**인 재공급만
현재 session의 실제 노출과 다른 활성 예약을 고정된 제외 스냅샷으로 만들어 전체 카탈로그 검색에 적용한다.
그 결과는 이전500 밖의 다음 후보도 포함할 수 있는 session 한정 pool이다. 같은 입력으로 일반500을 다시 만드는 것만으로 소진을 복구하지 않는다.

job/pool은 `excludedSessionId`, `excludedExposureRevision`, `excludedExposureHash`를 기록한다.
제외 ID는 정렬·중복 제거하여 hash를 검증하고, session의 노출 또는 활성 예약이 바뀔 때 exposureRevision을 증가시킨다.
게시 CAS에서 inputVersion·bundle·job token·기대 pool뿐 아니라 현재 active session과 제외 revision/hash도 비교한다.
새 노출/예약으로 제외 스냅샷이 달라졌으면 같은 결과를 게시하지 않고 supersede 후 새 스냅샷으로 다시 만든다.

일반 pool의 excludedSessionId는 null이다. session 한정 pool은 해당 session에서만 사용한다.
명시 새 탐색에서는 이전 session 한정 pool을 비활성화하고 공용500을 임시 사용하면서 새 job을 요청한다.
이전 session의 제외 목록을 새 session의 영구 제외로 이어 붙이지 않는다. 감상·관심없음 제외는 항상 유지한다.

발견 공급에서는0개인 그룹만 건너뛴다. “최대100”을 맞추려고11개째 공급 그룹을 방문하지 않는다.
게시된 발견≤100의 순서를 소비해도 발견 슬롯을 채우지 못하면, 미노출·미예약·미감상 조건으로 같은10×10 정책의 다음 공급을 한 번 준비한다.
그래도 발견을 못 채우면 POLICY에 따라 맞춤으로 대체하고 `actualType=PERSONALIZED`,
`fallbackReason=DISCOVERY_EXHAUSTED`를 기록한다. 대체 영화를 발견이라고 표시하지 않는다.

## 6. 2맞춤+1발견 노출과 동시 요청

- 최초 API045에서 추천 session을 만든다. 버퍼 소진·입력 변경·일반 추가 요청·재시도는 같은 session을 유지하고 이미 반환한 ID를 보존한다.
- Consumer는 정렬한 맞춤≤500·발견≤100을 게시한다. Spring은 각 라운드에서 현재 미할당 맞춤2편을 먼저 고른 뒤, 이2편을 포함한 공통 중복을 건너뛰어 발견1편을 고른다.
- 이 순서로10라운드를 조립한 **뒤** 최종 최대30슬롯을 예약한다. 정상 구성 목표는 맞춤20/발견10이다. 유형별 상위20/10을 먼저 잘라 놓고 조립하지 않는다.
- 응답 직전에 현재 감상·관심없음·정책 부적격 상태를 다시 확인한다. Consumer의 사전 제외는 이 검사를 대신하지 않는다.
- `LINK_CLICKED`는 팀의 노출 제외 조건으로 유지하되, 실제 감상 편수와 발견의 덜 본 그룹 분모에 자동 합산하지 않는다.
- 다음 요청은 현재 세트에서 다음 라운드를 사용한다. 같은 요청 ID 재시도는 같은 라운드 할당을 재사용하고 커서를 두 번 전진시키지 않는다.
- 사용자 상태/활성 세트 행 잠금으로 동시 요청의 중복 할당을 막는다. 영화 노출 기록과 라운드 진행을 같은 DB 트랜잭션에서 저장한다.
- 실제 노출·활성 예약의 생성/해제는 session의 exposureRevision도 같은 트랜잭션에서 갱신한다. 단순 재시도는 같은 revision과 할당을 재사용한다.
- 별점·온보딩·확정 감상·추천 필터 변경으로 `inputVersion`이 바뀌면 이전 미소비 세트는 stale이다. 세트 generation은 입력 버전과 분리하고 같은 session의 실제 노출은 보존한다.
- 관심없음은 같은 세트의 대체 기록으로 처리한다. 실제 별점·평가 편수·inputVersion을 바꾸지 않는다.
- 새 카탈로그가 게시돼도 이미 보여 준 세트 순서를 임의 변경하지 않는다. 삭제·새 부적격 영화는 제외하고 다음 세트부터 새 bundle을 사용한다.

새 탐색은 명시적인 `POST /recommendations/sessions`로 시작한다. `requestId` UUID와
`expectedSessionId`(최초에는 null)를 받고, 현재 session이 예상값과 일치할 때 새 session을 생성한다.
소유권을 확인하고 같은 requestId 재시도는 같은 session을 반환한다. 경합으로 예상 session이 바뀌면409다.
이전 세트의 미소비 예약은 해제하되 실제 노출 로그는 남긴다. 새 session은 감상·관심없음 제외를 계속 적용한다.
일반 pool을 재사용하더라도 새 session 기준의 제외로 재정렬을 요청한다. 이전 session 한정 pool과 순위는 새 탐색에 사용하지 않는다.
활동 시간 TTL로 session을 자동 초기화하지 않는다. 기존 API 번호를 임의로 붙이지 않고
로컬 operationId `startRecommendationSession`으로 추적한다.

## 8. 실패와 복구

| 실패 | 복구 규칙 |
| --- | --- |
| Kafka 발행 실패 | Outbox PENDING 유지·같은 eventId 재시도. 별점 저장은 이미 성공할 수 있음 |
| 역전/중복 이벤트 | 최신 DB 상태로 재계산. payload 값을 누적해 최신 상태를 추정하지 않음 |
| Consumer 계산/게시 중 종료 | 같은 job/version ID로 재시도. 일부 payload는 활성 포인터가 가리키지 않아 읽히지 않음 |
| Redis 부분 게시 | 불변 payload 저장 후 검증한 단일 active-pointer만 교체. 불일치 bundle 읽기 금지 |
| targeted job 실패 | 같은 bundle의 기존 pool membership+최신 재정렬 유지, refreshPending 기록. 새 후보가 생긴 것처럼 표시하지 않음 |
| 입력 변경 중 오래된 job 완료 | inputVersion·종류별token·pool 또는 ranking의 기대 활성 버전 조건으로 게시 거부 |
| 소진 backfill 중 노출/예약·session 변경 | excludedSessionId/exposureRevision/hash 조건으로 게시 거부. 새 스냅샷 작업 생성 |
| Redis 유실 | 현재 DB 입력과 정상 bundle으로 공용/개인 pool 복구. UUID를 재발급할 새 job과 재시도를 구분. 구키의 counter를1로 되돌려 재사용하지 않음 |
| 새 모델·배치 검증 실패 | 이전 완성 bundle 유지. 직전 정상 결과도 현재 inputVersion·최종 제외가 맞아야 사용 가능 |
| 대중 fallback까지 없음 | 추천만503/준비 상태로 처리. 검색·평가·감상 기능 유지 |

원본 RATING/ONBOARDING/입력변경 이벤트의 offset은 필요한 pool/ranking 작업 요청을 내부 Kafka에 내구성 있게
등록하고 Broker 성공 응답을 확인한 뒤 커밋한다. Spark 배치 작업의 완료까지 원본 이벤트를 동기로 붙잡지 않는다.
최초 접수에서 내구 저장한 job ID/payload를 전송 재시도에 재사용하며, 완료한 과거 작업의 token을 다시 활성화하지 않는다.
pool/ranking worker는 별도 실행 대기열 또는 Consumer Group으로 작업을 처리한다. **작업 메시지**의 offset은
결과 게시·후속 요청 전달이 성공하거나 superseded 처리를 끝낸 뒤 커밋한다. 실패한 작업은 같은 job/version으로 재시도하고
미완료 메시지를 성공 처리하지 않는다. 긴 Spark 실행 중에도 poll/heartbeat를 유지하는 실행 제어가 필요하다.
각 단계의 병렬 처리에서는 해당 파티션의 연속 완료 구간까지만 offset을 전진시킨다.
약한 행동은 eventId·event-time 기준으로 집계하고, 강한 입력의 inputVersion과 별도로 관리한다.

## 10. 상세 유사 영화의 준비와 운영

[SIMILAR-MOVIES](SIMILAR-MOVIES.md)의 독립 경로다. GKT 전처리·ID를 검증해 벡터를 export하고
서버 PostgreSQL에 버전별 적재/partial HNSW를 구성한다. 인덱스·예제 쿼리·응답을 검수한 뒤
