# FEELM 추천 데이터 인사이트 요약

> 대상: 팀 회의, Jira, 포트폴리오, 최종 보고서에서 재사용할 짧은 근거 모음

## 1. 사용자 입력은 많을수록 무조건 좋은가

입력이 많을수록 예상 별점 오차는 줄었다. 기존 실험에서 K1의 사용자별 MAE는 0.743, K10은 0.725,
K20은 0.714였다. 하지만 평가 가능한 사용자는 K0 20,271명에서 K10 16,795명, K20 14,644명으로 줄었다.

**해석:** 한 번에 25개를 강제하기보다 K5에서 시작하고 K10·K20을 추가 입력으로 유도하는 편이 현실적이다.
다만 추천 순위 개인화는 별도 Gate를 통과해야 한다.

## 2. 예상 별점과 추천 순위는 같은가

아니다. 기존 ALS 혼합은 K20에서 예상 별점 MAE를 K0보다 5.39% 개선했지만, 추천 순위 선택 결과는 모든
K에서 인기도 100%였다.

**해석:** 예상 별점 모델이 좋아졌다고 추천 ranking을 바꾸면 안 된다. 두 head를 분리해야 한다.

## 3. 한국 영화 데이터는 정말 없는가

목록은 있다. TMDB 한국-origin proxy는 11,680편이다. 문제는 MovieLens와 연결되는 영화가 1,056편이고,
그중 614편은 평점이 1~9개뿐이라는 점이다. 한국-origin 평점은 전체의 0.28%다.

**해석:** 한국 영화 카탈로그는 TMDB에서 가져올 수 있지만 협업 신호가 약하다. 콘텐츠 특징과 실제 서비스
피드백이 필요하다.

## 4. MovieLens에서 한국 사용자 성능을 알 수 있는가

알 수 없다. MovieLens 32M에는 사용자의 국가·나이 정보가 없다. 한국-origin 영화 10편 이상을 평가한
사용자는 1,379명이지만, 이들을 한국 사용자라고 부를 수 없다.

**해석:** 이 집단은 “한국 영화 상호작용이 상대적으로 있는 MovieLens 사용자” slice일 뿐이다.

## 5. 추천 정답이 없는 문제는 어떻게 다뤘나

미평가를 싫어요로 만들지 않았다. 사용자가 실제로 남긴 평점 중 20편을 고정 hash로 숨기고, 그 안에서만
상위 2편의 위험과 놓침을 채점한다.

**해석:** 미래 만족을 증명하는 실험은 아니지만, 같은 관측 영화에서 모델을 공정하게 비교하는 정적 선호
복원 실험이다.

## 6. 상위 2편 평가가 가능한가

가능하다. K10에서 16,795명이 20편 slate와 10편 input을 모두 만들 수 있고, 16,516명(98.34%)은 slate에
GOOD가 최소 한 편 있어 Miss를 채점할 수 있다.

**주의:** 98.34%는 추천 성능이 아니라 평가 정답이 존재하는 비율이다.

## 7. cold-item 실험 표본은 충분한가

strict Train 안에서 안전하게 density Validation을 나눈 결과 q≥5는 3,662편, q≥20은 1,963편, q≥100은
994편이었다. 5개 fold도 각 panel에서 최소 191편 이상이다.

**해석:** 표본 수 때문에 실험이 불가능한 것은 아니다. 다만 TMDB feature와 많은 재학습 비용이 남아 있다.

## 8. 가장 큰 실행 위험은 무엇인가

모델보다 데이터 역할 충돌이었다. 독립 영화 split 두 개가 6,964편에서 겹쳤다. density 역할을 strict
ITEM_TRAIN 안으로 제한해 0편으로 고쳤다.

**해석:** seed를 고정하는 것만으로 누출이 막히지 않는다. 여러 실험의 역할 교차표를 먼저 계산해야 한다.

## 9. 지금 제품에 반영할 수 있는 것은 무엇인가

- 현재 인기도 fallback 유지
- K5 빠른 시작, K10 추가 입력 유도라는 UX 가설
- 예상 별점은 로컬 실험으로만 유지
- 평가 완료·관심 없음 영화를 추천 목록에서 제외하는 제품 규칙 유지
- TMDB 특징 파일은 완성됐지만 Top-2 비교가 끝나기 전 개인화 표현 금지

## 10. 다음에 얻어야 할 데이터

1. REC-EV-019C 실제 입력 adapter·모델·block scorer·checkpoint의 구현·dry-run 결과
2. Validation 기준선·후보의 동일 후보 공간 예측
3. 결측이 많은 키워드에 덜 의존하는 구조·텍스트 ablation 결과
4. 서비스 출시 후 노출→상세→관심 없음→평가 이벤트
5. 한국-origin slice의 충분한 실제 사용자 피드백

## 11. TMDB 전체 특징에서 무엇을 알았나

100편 고정 표본에서 identity 99%, 구조·텍스트 100%를 확인한 뒤 Base 역할 사용자의 넓은 특성 집합
69,603편 전체를
실행했다. 링크 99.8635%, identity 98.8001%, 구조 특징 99.3112%, 텍스트 특징 99.7961%로 네 Gate를
모두 통과했다. 확인되지 않은 929편은 TV·미발견·ID 불일치로 분리해 자동 결합하지 않았다.

**해석:** MovieLens 링크를 그대로 정답으로 믿는 것보다 실제 TMDB 응답과 다시 대조하는 편이 안전하다.
특징 준비는 완료됐지만 추천 성능은 아직 아니다. 확인된 영화 중 키워드는 24.42%, 배우는 3.40%가 비어
있었다. 키워드 결측을 싫어요로 해석하거나 후보에서 제거하지 말고, missing mask와 B0 fallback을 유지한
상태에서 Validation 성능을 비교해야 한다.

## 12. 넓은 영화 정보와 실제 추천 후보는 왜 다른가

69,603편은 Base 역할 사용자가 전체 기간에 평가한 영화라 미래 시점 영화도 섞여 있다. 실제 학습 cutoff
이전에 나온 영화는 42,203편이고, TMDB 링크를 거쳐 42,123편, 신원 확인까지 거쳐 41,625편이 남았다.

**해석:** 더 많은 영화 특징을 준비한 것은 좋지만 그 집합을 그대로 후보로 쓰면 미래 정보가 섞인다. 019C는
항상 41,625편의 동일 후보에서 모델을 비교해야 한다.

## 13. 실제 모델 실험에 필요한 사용자는 남았나

사용자 역할을 완전히 분리하고 입력 10개·이후 평점 10개·좋은 영화 3개·후보 안 좋은 영화 1개 조건을
적용한 Locked Test 사용자는 5,476명이다. TMDB 신원 확인을 적용해도 추가 탈락은 없었다.

**해석:** 최소 5,000명 Gate는 통과했다. 다만 이는 추천 성능이 좋다는 뜻이 아니라 공정한 최종 비교를 할
정답 집합이 충분하다는 뜻이다. 019C 실행 계약은 통과했지만 runner·합성 preflight와 Validation 선택이
끝나기 전에는 이 Test의 모델 성능을 열지 않는다.

## 14. role 열만 분리하면 Test 누출이 막히는가

아니다. 처음 019A artifact는 Router·Validation·Locked Test 행을 한 Parquet에 넣고 role 열로만 구분했다.
필터를 올바르게 쓰더라도 Validation 프로세스가 Test 정답이 든 파일을 이미 열 수 있는 구조였다.

**해석:** 통계적인 역할 분리뿐 아니라 물리적인 파일 접근 경계도 필요하다. Router·Validation·Locked Test의
prefix와 평가 window를 각각 별도 파일로 만들고, 019C runner는 Validation 두 파일만 open 전에 allowlist
검사하도록 계약했다. 이 변경 뒤에도 최종 후보 41,625편과 K10 Test 5,476명은 그대로다.

## 15. 추천 라이브러리의 loss 이름만 보고 써도 되는가

안 된다. LightFM의 BPR/WARP는 미관측 항목을 negative 후보로 샘플링한다. 이는 FEELM의 “미평가는
UNKNOWN” 원칙과 충돌하므로, B8은 관측 LIKE/DISLIKE만 `+1/-1`로 쓰는 logistic loss로 바꿨다.
새 사용자는 학습된 item·content 표현을 고정하고 사용자 vector만 별도로 fold-in한다.

**해석:** 같은 “BPR” 이름이어도 B4는 실제 관측 LIKE>DISLIKE pair만 직접 만들 수 있지만, B8 LightFM의
pairwise 구현은 다른 negative 의미를 가진다. 라이브러리 선택은 논문 이름보다 실제 sampling semantics를
계약과 대조해야 한다. 고정 Linux 환경의 9개 smoke 검사는 통과했지만 추천 성능은 아직 측정하지 않았다.

## 16. 대용량 실행에서 무엇을 배웠나

TMDB 전체 수집에는 약 2시간 6분이 들었고 112,580개 응답 cache가 생겼다. embedding은 한 차례 93.2%에서
세션이 끊겨 batch checkpoint가 없으면 거의 전부를 다시 계산해야 했다. checkpoint와 입력 hash signature,
길이순 stable batching을 추가한 뒤 전체 68,674편 embedding을 완성했다.

**해석:** 대용량 추천 프로젝트에서 “모델이 돌아간다”보다 재시작 비용·cache 정합성·결과 checksum을 먼저
설계해야 한다. 그래야 LLM이나 사람이 긴 실행을 중단·재개해도 같은 결과를 이어서 만들 수 있다.
