# 포트폴리오용 — 추천 평가 문제 해결과 AI 활용 경험

> 용도: 자기소개서, 면접, 회고 발표, 포트폴리오 본문에 맞게 골라 쓸 수 있는 원본
> 주의: “AI가 다 만들었다”가 아니라 어떤 판단을 사람이 했고 AI를 어떻게 검증했는지 보여 준다.

## 1. 30초 요약

영화 추천 프로젝트에서 MovieLens의 숨긴 영화가 Top-500 안에 있는지만 보던 평가가 실제 서비스의
상위 2편 품질을 설명하지 못한다는 문제를 발견했습니다. 미평가를 싫어요로 보지 않고, 사용자별 평점
성향을 반영한 20편 평가판을 만든 뒤 상위 2편의 위험과 놓침을 따로 측정하도록 평가를 다시 설계했습니다.
AI로 논문·기술 후보를 넓게 조사하고 계약·검증 코드를 빠르게 만들되, 다른 대화 세션의 독립 감사를 반복해
누출과 통계 정의 오류를 찾았습니다. 실제 사전검사에서는 영화 분리 충돌 6,964편을 발견해 0편으로 고쳤고,
69,603편 TMDB 전체 특징도 품질 Gate와 재시작 가능한 pipeline으로 완성했습니다. 이어 시간 cutoff를
지킨 최종 후보 41,625편과 K10 평가 사용자 5,476명을 고정했습니다. 새 모델이 인기도보다
낫다는 근거가 생기기 전까지 기존 정책은 유지했습니다.

## 2. 문제 해결 과정

### 상황

- 서비스는 요청할 때마다 추천 2편을 보여 준다.
- MovieLens에는 사용자가 평가한 영화만 있고, 미평가 영화의 만족도는 알 수 없다.
- 한국 영화는 TMDB 목록은 많지만 MovieLens 평점이 매우 적다.
- 기존 지표는 후보 500개 안에 정답이 있는지 중심이라 상위 2편의 실패를 가렸다.

### 처음 가정이 왜 틀렸나

처음에는 시간 순서로 마지막 평가를 숨기거나, 500개 후보에 숨긴 영화가 들어오는지를 보려 했다. 하지만
MovieLens의 timestamp는 본 날짜가 아니라 평점을 입력한 날짜일 수 있다. 또 사용자가 평가하지 않은 영화는
싫어한 영화가 아니다. 이 방식으로 실제 만족을 주장하면 데이터가 말하지 않는 내용을 덧붙이게 된다.

### 목표를 다시 정의

완벽한 추천 정답을 만들려 하지 않고, 관측된 평점 안에서 다음을 비교하기로 했다.

1. BAD 영화를 상위 2편에 올리지 않는가?
2. GOOD 영화가 있었는데도 상위 2편에서 모두 놓치지 않는가?
3. 결과가 일부 사용자에게만 좋은 것은 아닌가?

### 실행

- 사용자를 Base Train / Router Train / Validation / Locked Test로 hash 분리했다.
- 사용자마다 관측된 평점 20편을 label을 보지 않는 고정 hash로 뽑았다.
- 평점 후함·짬 차이를 줄이기 위해 사용자 내부 상대 순위로 GOOD/BAD를 정의했다.
- K=0/1/3/5/10/20/30/50에서 평가 가능한 사용자를 셌다.
- 모델 비교 전 단계에서 schema, artifact contract, unit test, checksum verifier를 만들었다.
- cold-item 실험에서는 strict 역할과 density 역할의 교차표를 실제로 계산했다.

### 발견

- K=10에서 16,795명이 구조적으로 평가 가능했다.
- 16,516명은 GOOD opportunity가 있어 Miss를 채점할 수 있었다.
- 별도 영화 분리 두 개가 6,964편에서 충돌했다.
- density 역할을 strict ITEM_TRAIN 안으로 제한해 충돌을 0으로 만들었다.
- 과거 ALS 실험은 K가 늘수록 예상 별점 MAE를 줄였지만 추천 순위는 인기도를 이기지 못했다.
- Base 역할 사용자의 넓은 69,603편 TMDB 특성 집합에서 링크·identity·구조·텍스트 Gate를 모두 통과했다.
- 이 69,603편을 후보로 잘못 부른 경계를 발견하고, cutoff-safe 42,123편과 신원 확인을 합친 41,625편만
  실제 후보가 되도록 계약과 검증기를 교정했다.
- K10 Locked Test 엄격 적격 5,476명으로 최소 5,000명 Gate를 통과했지만 모델 성능은 열지 않았다.
- 역할 값은 나뉘어 있어도 한 Parquet에 Validation과 Locked Test가 같이 있으면 코드가 Test 정답을
  물리적으로 읽을 수 있음을 발견했다. 역할별 파일로 다시 만들고 입력 allowlist로 open 전 차단했다.
- LightFM BPR/WARP가 미관측 항목을 negative로 샘플링해 “미평가는 UNKNOWN” 규칙과 충돌함을 실제
  dependency smoke 전에 발견했다. B8을 관측 ±1 logistic과 frozen-item fold-in으로 교정했다.
- 키워드는 24.42%가 비어 있어 단일 메타데이터에 의존하는 모델이 위험하다는 것을 확인했다.

### 결정

새 모델을 억지로 champion으로 정하지 않았다. TMDB 특징 파일은 완성했지만 새 Validation 비교가 끝날
때까지 인기도 기준선을 유지했다. 실패를 숨기지 않고 “특징 준비 완료, 예상 별점은 가능성, 추천 순위는
미검증”으로 분리했다. 019C의 7개 모델·탐색 수·score 변환·fallback·checkpoint를 계약으로 잠갔지만,
계약 PASS를 모델 성능 PASS로 바꾸지 않았다. 합성 runner 15개와 Linux dependency 9개를 통과한 뒤에도
실제 Validation runner 구현까지만 다음 권한으로 열었다.

## 3. AI를 어떻게 사용했나

### AI가 잘한 일

- 추천 평가 논문·산업 사례의 후보를 빠르게 모음
- 여러 평가 방법의 장단점을 표로 비교
- 프로토콜 JSON, artifact contract, 테스트 골격을 반복 생성
- 서로 다른 대화 세션에서 같은 설계를 독립적으로 공격 검토
- 긴 문서 사이의 용어·수식·파일 경로 불일치 탐색
- 3,200만 평점 사전검사 코드와 보고서 그래프 생성 자동화

### 사람이 직접 결정한 일

- “쓰레기 같은 영화 추천이 최악”이라는 제품 우선순위
- 상위 2편을 primary로 볼 것
- 미평가를 싫어요로 처리하지 않을 것
- MovieLens는 사용자 행동, TMDB는 영화 정보로 역할을 분리할 것
- 추천 순위가 개선되지 않으면 예상 별점 개선만으로 채택하지 않을 것
- Locked Test와 제품 정책을 함부로 열거나 바꾸지 않을 것

### AI 답변을 그대로 믿지 않은 방법

1. 설계 초안 작성
2. 새 대화 세션에 문맥을 최소화한 감사 프롬프트 전달
3. HIGH 지적을 protocol·JSON·backlog에 반영
4. 다시 새 세션에서 재감사
5. 수식은 golden fixture로 코드에서 고정
6. 실제 전체 데이터 preflight로 구조적 누출 확인

이 과정에서 사람 유사성 NDCG gain, agreement 수식, bootstrap 단위, 영화 역할 충돌 같은 문제가 여러 번
발견됐다. 이후에는 “행에 role 열이 있다”는 논리 분리만으로 충분하지 않고, 실행 코드가 열 수 있는 파일
자체를 분리해야 한다는 문제도 잡았다. AI 생산량은 컸지만, 독립 검증과 실행 계약이 없었다면 오류도 같은
속도로 늘어났을 것이다.

또 라이브러리 이름만 보고 알고리즘을 채택하지 않았다. LightFM 공식 loss 의미를 계약의 UNKNOWN 처리와
대조해 BPR/WARP를 기각했고, 고정 Linux 이미지에서 hash-locked wheel을 설치해 signed logistic 학습과
item 표현을 바꾸지 않는 사용자 fold-in을 실제로 확인했다.

### 실제 API 실행에서 AI 오류를 잡은 사례

TMDB 100편 사전 실행의 첫 결과는 100편 모두 401이었다. AI가 환경 변수 이름만 보고 값도 JWT Read
Access Token이라고 가정했지만, 실제 로컬 값은 v3 API key였다. credential을 출력하지 않고 길이·형식과
TMDB 상태 코드만 확인해 원인을 찾았고, 두 인증 방식을 안전하게 구분하도록 수정했다.

더 중요한 문제도 있었다. 처음 verifier는 파일 schema와 embedding 형식만 확인해 identity 0% 결과도
통과시켰다. “코드가 실행됐다”와 “쓸 수 있는 데이터가 나왔다”를 혼동한 것이다. 사전검사에도 identity
98%, 구조·텍스트 95% 하한을 넣고, 실패 결과가 PASS가 될 수 없게 바꿨다. 수정 후 실제 결과는 identity
99%, 구조·텍스트 100%였으며 IMDb 불일치 1편은 검토 대상으로 격리했다.

이 사례의 핵심은 AI가 많은 코드를 만든 것이 아니라, 실패를 숨기지 않고 **가정 → 실제 호출 → 반례 →
계약 강화 → 재실행** 순환으로 바꾼 점이다.

### 긴 실행을 실패해도 이어 가게 만든 사례

전체 TMDB API 수집은 약 2시간 6분이 걸렸고 112,580개 응답이 cache됐다. embedding 실행은 93.2%에서
세션이 끊겼는데, 처음 구현에는 batch checkpoint가 없어 긴 계산을 그대로 재개할 수 없었다. 이를 단순
재실행으로 덮지 않고 메모리맵 checkpoint, 모델·입력 hash signature, batch별 flush를 계약에 추가했다.

또 텍스트 길이순으로 묶어 낭비되는 padding을 줄이되 원래 영화 순서를 복원하도록 만들었다. 100편의 이전
벡터와 비교해 최대 절대 차이가 `0.0`임을 확인한 뒤 전체 68,674편 embedding을 완성했다. 마지막 재검증은
network request 0회로 cache만 사용했고 manifest SHA-256까지 통과했다.

이 경험에서 얻은 핵심은 LLM의 생산량을 “한 번에 많은 코드를 쓰는 능력”이 아니라 **장시간 작업을
중단·검증·재개할 수 있는 실행 계약을 빠르게 강화하는 능력**으로 사용해야 한다는 점이다.

### 모델을 돌리기 전에 75억 회 계산을 발견한 사례

합성 검사가 통과했다고 바로 전체 실험을 실행하지 않았다. 실제 Parquet 값은 읽지 않고 footer의 행 수와
trial·seed 계약을 곱하는 metadata-only 점검을 추가했다. 그 결과 전체 후보 점수 계산 약 75.5억 회,
LightFM 학습 update 최대 약 61.5억 회, BPR pair 수 미정이라는 문제를 찾았다.

이 결과로 “많이 반복하면 더 믿을 수 있다”는 막연한 설계를 폐기했다. 모든 설정은 고정 seed 17과
256명/K tuning panel에서 비교하고, 선택한 설정만 5개 seed로 패널 안정성을 확인하며 seed 17로 전체
Validation을 계산하도록 계약을 다시 짰다. BPR pair도 사용자당 epoch 최대 16개로 고정했다. 재점검에서는
score 약 15.8억, LightFM 최대 12.3억, BPR 최대 3.93억 update로 정해 둔 예산을 모두 통과했다. AI를 실행
속도뿐 아니라 **실행 전에 실패 비용을 수치로 드러내고 계약으로 줄이는 도구**로 사용한 사례다.

## 4. 면접에서 강조할 포인트

### 문제 해결

> 정확도 숫자를 높이는 것보다 “무엇을 정답이라고 부를 수 있는가”부터 다시 정의했습니다. 서비스가 실제로
> 2편만 보여 주기 때문에 Top-500 recall이 아니라 Top-2 harm와 miss를 primary로 바꿨습니다.

### 데이터 인사이트

> 한국 영화 문제는 카탈로그 부족보다 상호작용 밀도 부족이었습니다. TMDB에는 한국-origin proxy가
> 11,680편 있었지만 MovieLens와 연결된 영화는 1,056편, 그중 614편은 평점이 1~9개뿐이었습니다.

### 기술 선택

> Spark·ALS·TMDB embedding을 먼저 넣지 않았습니다. 3,200만 평점을 hash split하고 사전검사를 통과한 뒤,
> 모델 실행 횟수와 데이터 누출 경계를 확인했습니다. 필요한 처리 방식이 확인된 뒤 기술을 쓰는 순서였습니다.

### AI 활용

> AI는 초안과 구현 속도를 높이는 역할로 쓰고, 의사결정은 protocol lock, golden fixture, 독립 세션 감사,
> 전체 데이터 preflight로 검증했습니다. 특히 AI가 만든 두 독립 split이 실제로는 6,964편에서 충돌한다는
> 문제를 실행으로 찾아 수정했습니다.

> TMDB 실행에서도 처음에는 인증 형식을 잘못 가정해 100편 모두 401이었고, verifier까지 그 결과를
> 통과시키는 결함이 있었습니다. credential 형식을 안전하게 구분하고 coverage Gate를 verifier에 추가해
> 재실행한 결과 100편 사전검사를 통과했고, 이어 전체 69,603편에서도 identity 98.80%, 구조 99.31%,
> 텍스트 99.80%로 계약 Gate를 통과했습니다. 이후 69,603편은 미래 영화가 섞인 특징 집합이지 후보가
> 아니라는 의미 오류도 발견해, 실제 추천 후보를 41,625편으로 별도 고정했습니다.

## 5. STAR 형식 예시

### Situation

영화 추천 팀 프로젝트에서 공개 데이터가 외국 인기 영화에 치우쳐 있고, 실제 추천 만족 정답이 없어 모델
성능을 설득하기 어려웠다.

### Task

사용자가 거의 없는 상황에서도 거짓 만족도 주장을 하지 않으면서, 모델 교체 여부를 판단할 재현 가능한
오프라인 평가를 설계해야 했다.

### Action

사용자별 상대 평점과 고정 20편 slate를 만들고 Top-2 harm/miss를 정의했다. 데이터 역할을 MovieLens 행동과
TMDB 영화 정보로 분리했다. AI로 문헌 조사와 계약·코드를 빠르게 만들고, 독립 감사와 golden fixture를
반복했다. 3,200만 평점 전체 preflight와 영화 역할 교차표를 실행했다.

### Result

K=10에서 16,795명의 평가 표본과 98.34%의 miss 채점 가능률을 확인했다. 영화 역할 충돌 6,964편을 0편으로
수정하고, 전체 69,603편 TMDB 특징 pipeline의 네 품질 Gate를 통과했다. 시간 누수를 막은 후보 41,625편과
K10 평가 사용자 5,476명도 고정했다. 동시에 기존 ALS가 예상 별점은 개선했지만 추천 순위는 개선하지
못했다는 사실을 분리해 근거 없는 champion 교체를 막고, 다음 Validation 모델 비교의 재현 가능한 입력을
만들었다.

## 6. 과장하면 안 되는 표현

- “추천 정확도를 98.34% 달성” → 틀림. 이는 채점 가능한 사용자 비율이다.
- “한국 사용자 추천을 검증” → 틀림. MovieLens에는 국가·연령 정보가 없다.
- “ALS가 5.39% 추천 성능 개선” → 틀림. 예상 별점 MAE 개선률이다.
- “cold-start 해결” → 틀림. 실험 표본·firewall·TMDB 특징은 준비됐지만 모델 성능 결과는 없다.
- “AI가 자동으로 최적 모델을 완성” → 틀림. AI는 설계·구현을 보조했고 제품 채택은 보류됐다.
