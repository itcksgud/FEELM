# FEELM 추천 전체 설계 — 무엇을, 언제, 어떻게 추천하는가

상태: **DRAFT · 로컬 최종 선정안** · 2026-09-13  
범위: 개인 맞춤·발견 추천의 입력, 후보, 점수, 갱신, 2편씩 추가 노출. 팀의 승인·구현·배포 완료 기록은 아니다.

**평가가 적을 때는 대중평가와 한국 흥행 자료를 중심으로 추천한다. 실제 별점 10편부터는
GBT로 개인 선호를 예측하고, ALS가 계산 가능한 영화에는 평가 근거량만큼 ALS를 함께 쓴다.
발견 추천은 덜 본 하위 그룹에서 후보를 찾은 뒤 같은 개인 예측기로 정렬한다.
두 방식 모두 처음 2편, 추가 요청마다 2편을 보여준다.**

## 1. 이번에 정리한 선택

| 결정할 것 | 로컬 선정안 | 이 선택의 성격 |
| --- | --- | --- |
| 개인 예측 모델 | `GBT120_s339` + 지원량에 따른 ALS 보조 `shrink100` | 기존 모델·제한된 보조 정책 비교를 재사용 |
| 개인 예측 전환 | 실제 별점 **10편**부터 | 운영 기본값. 최적 K를 입증한 것은 아님 |
| 모델에 넣는 이력 | **최신 원본 별점 10편**. 전체 이력은 보존 | 기존 비교의 입력 상한 유지 |
| 화면 반환 | 기본 맞춤 2편, 발견을 요청하면 발견 2편. 각 경로에서 2편씩 추가 | 이번 문서의 화면 연결안. 기존 맞춤2+발견1과 다름 |
| 발견 분류 | **8맛 × 맛당 128개 = 총 1,024개 하위 그룹** | 사용자 방향 + 기존 K128 실험 재사용 |
| 발견 계산량 | 그룹별 최대 25편, 합계 최대 100편을 점수화 | 기존 K128의 계산 예산 유지 |
| KOBIS 반영 | 초기 추천과 발견의 **한국 흥행 후보 확보** | 새 운영 정책. 추천 품질 개선 실험 결과는 아님 |
| GBT 갱신 | 별점이 바뀌면 사용자 특징과 예측만 다시 계산 | 나무 재학습과 구분 |
| 모델 재학습 | 한 달 프로젝트에서는 검증된 모델을 고정. 학습 자료·특징 변경 때만 별도 실행 | 운영 복잡도를 제한하는 결정 |

이 문서는 결정을 다시 무한 탐색으로 돌리지 않는다. **선정한 로직과 근거를 정리한 문서이며,
아직 없는 서비스 연결 코드를 구현했다고 표현하지 않는다.**

## 2. 평가 편수 K마다 무엇을 쓰는가

`K`는 현재 남아 있는 **서로 다른 영화의 실제 별점 편수**다. 같은 영화 수정은 1편이고,
삭제하면 감소한다. 온보딩 LIKE/DISLIKE·조회·관심없음은 K에 넣지 않는다.

| 사용자 상태 | 맞춤 화면의 추천 | 발견 요청 처리 |
| --- | --- | --- |
| K=0, 온보딩 선택 없음 | TMDB 보정 대중평점 목록과 KOBIS 한국 흥행 목록을 번갈아 사용 | 같은 초기 추천을 제공하고 개인화 발견으로 표시하지 않음 |
| K=0, 온보딩 선택 있음 | 선택 영화의 콘텐츠 방향으로 그룹 순서를 정하고 그룹 안에서는 대중 자료 사용 | 초기 추천으로 제공. 실제 감상 경험을 추정하지 않음 |
| K=1~9 | 실제 별점으로 만든 콘텐츠 방향을 우선 사용하고, 대중 자료 중심으로 후보 선정 | 초기 추천으로 제공. 개인 별점 예측은 아직 사용하지 않음 |
| K=10~29 | GBT + 지원량에 따른 ALS 보조로 개인 순위 계산 | 덜 본 하위 그룹 → 대중 자료 후보 → 같은 개인 예측기로 정렬 |
| K≥30 | 같은 개인 예측기 유지. 입력은 최신 10편 | 같은 발견 정책 유지. 덜 본 그룹 판단에는 전체 실제 감상 이력 사용 |
| K≥10이어도 GBT 입력을 만들 수 없음 | 초기 추천으로 복귀하고 사유 기록 | 콘텐츠 방향이 있어도 개인화 발견 대신 초기 추천 |
| K≥10, GBT 가능·콘텐츠 방향 없음 | 맞춤 개인 예측은 유지 | 개인화 발견 대신 초기 추천을 제공하고 유형 구분 |

**10은 서비스 전환 편수, 최신 10은 모델 입력 상한, 128은 군집 수다. 서로 다른 숫자다.**
과거 입력량 비교는 더 많은 별점이 오차를 줄일 수 있음을 보였지만, K30에서 새로운 모델로
자동 교체할 근거는 없다. 현재 보정·비교 조건을 유지하기 위해 최신 10편을 기본값으로 둔다.
현재 GBT 결합과 새 대중 교대 정책을 직접 비교해 K10 전환의 우위를 확인한 실험은 아니다.

LIKE/DISLIKE는 별도로 보관한다. 예전에 계산했던 LIKE=4.2712, DISLIKE=2.7984는 특정
ALS 입력 비교의 추정값이었다. 이번 GBT 실제 별점 경로에는 그 값을 실제 별점처럼 넣지 않는다.
초기 추천에서만 `LIKE 콘텐츠 합 − DISLIKE 콘텐츠 합`의 방향을 사용한다.
실제 별점 방향이 유효하면 그것을 우선하고 온보딩 방향을 중복 합산하지 않는다.

## 3. 맞춤 추천: 사용자 입력부터 두 편까지

```text
실제 별점 등록·수정·삭제
 → 최신 DB 이력 확인
 → K와 최신 원본 10편 결정
 → 영화 정보 + 사용자의 반응 + 근거 편수로 모델 입력 생성
 → 서비스의 적격 영화 전체를 비동기로 점수화
 → 이미 본 영화·관심없음·현재 세션 노출 영화 제외
 → 개인 점수순 목록 저장
 → 처음 2편, 요청하면 다음 2편
```

GBT는 사용자마다 새로 만드는 모델이 아니다. **공유 모델 하나가 사용자별 입력을 받아
서로 다른 점수를 계산한다.** 장르·국가·연도·인물 등 영화 정보, 그 정보에 대한 사용자의
기존 별점 반응, 일치한 영화 편수, 대중평가 관련 반응 등을 기존 230개 특징으로 만든다.
신규 영화도 이 특징을 만들 수 있으면 점수화할 수 있다.

개인 점수는 다음으로 고정한다. 보정 함수는 기존 실험에서 고정한 것을 재사용한다.

```text
ALS 계산 불가능: 개인 점수 = 보정 GBT
ALS 계산 가능:   개인 점수 = a × 보정 ALS + (1−a) × 보정 GBT
                 a = 해당 영화의 MovieLens 학습 평가 수 / (그 수 + 100)
```

ALS에는 후보 영화 factor와 이를 이용할 수 있는 사용자 입력이 모두 필요하다.
예를 들어 학습 평가가 1·10·100·1,000개인 영화의 ALS 비중은 약 1%·9%·50%·91%다.
여기의 평가 수는 TMDB 투표 수나 KOBIS 관객 수가 아니다.

**맞춤 후보를 ALS Top500 안으로 제한하지 않는다.** 그러면 ALS에 없는 영화를 추천하려는
목적을 다시 막기 때문이다. 사용자 수가 적은 이번 프로젝트에서는 전체 적격 카탈로그의
점수 계산을 비동기 작업으로 두고, 화면은 저장된 순위를 읽는다. 계산 블록 크기와 Redis
저장량은 메모리 설정이며 추천 가능한 영화 범위를 정의하는 임계값이 아니다.

## 4. 발견 추천: 그룹 비교와 영화 비교를 나눈다

```text
전체 감상 이력으로 덜 본 하위 그룹 찾기
 → 최신 별점 10편으로 만든 사용자 콘텐츠 벡터와 그룹 대표 비교
 → 가까운 적격 그룹부터 방문
 → 그룹별 TMDB 대중평가 후보 + KOBIS 한국 흥행 후보 확보
 → 최대 100편에 개인 예측기 적용
 → 상위 10편 버퍼, 2편씩 제공
 → 버퍼 소진 후 이미 노출한 영화를 빼고 다음 후보 계산
```

상위 8맛은 고정된 장르 기반 분류이고, 각 맛 안의 128개 그룹은 **장르·키워드·줄거리**를
함께 사용한다. 사용자를 한 맛에 가두지 않고 모든 적격 하위 그룹을 비교한다.

덜 본 그룹은 **그 그룹의 감상 영화가 2편 이하이고 전체 감상 영화의 20% 이하**인 그룹이다.
그 안에 추천 가능한 미시청 영화도 있어야 한다. 높은 별점을 준 영화만 세지 않는다.
같은 팝콘 맛 안의 다른 하위 그룹도 발견 후보가 될 수 있으므로 “처음 보는 팝콘 맛”이라고
일괄 설명하지 않는다.

그룹과 사용자는 콘텐츠 벡터의 내적으로 비교한다. **그룹이 가까운가**를 먼저 확인하고,
뽑힌 영화는 GBT+ALS로 **사용자가 좋아할 가능성이 높은가**를 다시 계산한다.
KOBIS·TMDB는 그 사이에서 후보를 공급한다. 군집 번호나 관객 수를 개인 예상 별점에 더하지 않는다.

## 5. KOBIS를 어디에 넣는가

현재 수집한 **한국영화 200편·외국영화 200편의 KOBIS 통합전산망 누적 흥행 표본**을 비교했다.
보수적 조건으로 연결한 영화는 371편이고, 세 자료의 양수 기록이 연결된 영화는 338편이다.
그중 MovieLens 종료 이후 개봉한 것으로 표시된 1편을 별도 분리해 주요 통계는 **337편**을 썼다.

| 영화 | KOBIS 통합전산망 누적 관객¹ | MovieLens 평가 수 | TMDB 투표 수 |
| --- | ---: | ---: | ---: |
| 명량 | 17,616,791 | 83 | 338 |
| 극한직업 | 16,266,641 | 75 | 368 |
| 어벤져스: 엔드게임 | 13,977,409 | 11,811 | 28,571 |
| 범죄도시 3 | 10,682,813 | 6 | 565 |
| 기생충 | 10,317,318 | 11,670 | 21,242 |

¹ 2026-09-13 현재 조회. 2004년 이후 연동률·재개봉·보정의 영향을 받는 발권 집계이며
전체 시기 관객을 완전하게 복원한 수치가 아니다.

이 차이는 **국내에서 많이 본 영화를 MovieLens 평가 수만으로 찾으면 놓칠 수 있다**는
근거다. 한국영화 전체에 같은 가산점을 줄 근거나, 관객 수가 개인 만족도를 뜻한다는 근거는 아니다.
최신 누적 KOBIS·보유 TMDB와 2023년에 종료된 MovieLens의 비교이며 시점이 일치하지 않는다.

이번 운영안은 다음처럼 정한다.

| 적용 위치 | 방법 |
| --- | --- |
| 아무 선호도 없는 초기 추천 | TMDB 보정 대중평점순과 국내 누적 관객순을 **1편씩 교대**, 중복 제거 |
| 선호 방향이 있는 초기 추천 | 가까운 그룹부터 아래의 그룹별 후보 정책을 사용. 그룹 내 두 목록을 교대로 제공 |
| 개인화 발견 | 각 그룹에서 **TMDB 후보 20편 + 중복되지 않는 KOBIS 후보 최대 5편**. 부족분은 남은 목록에서 보충해 최대 25편 |
| K≥10 맞춤 최종 순위 | 개인 예측 점수 유지. KOBIS 관객 가산점이나 한국 제작국 가산점을 추가하지 않음 |

20:5와 초기 1:1은 **두 자료가 후보에 참여하게 하는 운영 기본값**이며 성능 최적 비율이 아니다.
KOBIS 후보도 최종 개인 예측 순위를 거치므로 최종 2편 중 한국 흥행 영화가 반드시 1편
포함되는 것은 아니다. 외국영화의 한국 흥행도 같은 KOBIS 목록에 포함한다.

이미 전체 영화를 점수화하는 맞춤 경로에 KOBIS 후보를 단순 합쳐도 순위가 바뀌지 않는다.
따라서 그것을 “한국 취향 보정”이라고 주장하지 않는다. 한국 환경 자료를 반영하는 실제
위치는 **초기 추천과 발견 후보 선정**이다. KOBIS가 없는 OTT 영화도 자동 감점하지 않는다.

[박스오피스·평가 자료 비교와 전체 수치](KOBIS-DATA.md)에서 표본 범위, 매출, 결측과 출처를 확인할 수 있다.

## 6. 별점을 넣으면 무엇이 바뀌는가

| 변화 | 다시 계산하는 것 | 다시 학습하는 것 |
| --- | --- | --- |
| 별점 등록·수정·삭제 | K, 최근 이력, 사용자 반응 특징, ALS fold-in, 개인 점수, 발견 후보 | 없음 |
| 확정 감상 이력 등록·삭제 | 시청 제외, 그룹별 경험량, 발견 버퍼와 후보. 입력 버전도 갱신 | 없음 |
| 새 영화 또는 영화 정보·투표·관객 갱신 | 영화 특징, 고정 중심 배정, 대중 목록, 필요한 사용자 추천 | 없음 |
| 학습 자료 또는 특징 정의 변경 | 새 산출물 검증 후 추천 전체 버전 전환 | 별도 배치에서 새 모델 학습 |

Spark는 큰 데이터의 정제·특징 생성·그룹별 목록과 오프라인 학습을 맡는다. Python Consumer는
이벤트가 오면 최신 사용자 이력으로 예측한다. Redis는 결과를 저장하고 Spring은 제외 조건과
2편 페이지를 처리한다. Spark Streaming은 전역 행동 집계를 맡고 사용자마다 GBT를 재학습하지 않는다.

일반 카탈로그·대중 목록은 매일 06:00 KST 갱신을 운영 기본값으로 둔다. 실패하면 마지막 정상
스냅샷을 유지하고 시각을 기록한다. **이번 작업에서 스케줄러나 외부 서비스를 설정한 것은 아니다.**
