# 추천 운영과 갱신 — 맞춤·발견 A–Z 보충 문서

상태: **DRAFT — 로컬 선정안. 팀의 API·DB·Redis·모델 계약은 변경하지 않았다.**  
작성일: 2026-09-13. 한 달 팀 프로젝트에 적용할 운영 기준을 정리한 문서이며, 구현·배포 완료 보고가 아니다.

**별점이 바뀔 때는 사용자 특징과 추천 결과를 다시 계산한다. GBT 나무를 다시 학습하지 않는다.**
영화 정보와 대중 지표는 일별 배치로 갱신하고, 서비스 실행 중에는 검증한 모델을 고정한다.

## 1. 어떤 추천을 언제 제공하는가

| 구분 | 로컬 선정안 | 혼동하지 않을 점 |
| --- | --- | --- |
| 개인화 전환 K | 서로 다른 영화에 대한 현재 실제 별점이 10편 이상 | 수정은 1편으로 유지하고 삭제는 차감한다. 클릭·관심없음·LIKE/DISLIKE 선택은 이 편수에 합산하지 않는다 |
| 개인화 입력 H | 최신 실제 별점의 원본 10편 | 매핑 전에 10편을 자른다. 매핑되지 않은 영화를 과거 영화로 채워 넣지 않는다 |
| K=0~9 | 대중 자료 중심으로 초기 선택·콘텐츠 방향을 반영 | 별점 예측 모델의 개인화 추천으로 표시하지 않는다. 구체적인 초기 경로는 POLICY-DETAILS 3절을 따른다 |
| K≥10 맞춤 | `GBT120_s339` + ALS `shrink100` 보조 | 서비스의 전체 적격 영화가 출발점이다. ALS Top500으로 잘라서 시작하지 않는다 |
| K≥10 발견 | 팝콘 8맛 × 맛당 하위 128그룹 = **총 1,024그룹** | 128개 전체 그룹이라는 뜻이 아니다. 하위 그룹은 내부 검색 단위이며 맛 8개 UI와 분리한다 |
| 표시 | 기본 화면은 맞춤 최대 2편, 사용자가 발견을 요청하면 발견 최대 2편 | 같은 유형으로 2편씩 계속 제공한다. 기본 세트에 발견 1편을 자동 삽입하지 않는다 |
| 결과 준비 | 맞춤은 전체 적격 후보를 비동기로 점수화, 발견은 최대 100개를 점수화해 Top10 준비 | 후보 계산 수·결과 보관 수·화면에 보이는 2편은 서로 다른 수다 |

K는 입력 부담과 기존 검증 범위를 고려한 운영 기준이다. **10편이 모든 사용자에게 통계적으로 최적인 전환점이라는 결론은 아니다.**
10편 이상이어도 사용할 영화 정보가 없어 개인 특징을 만들 수 없다면 대중 추천으로 돌아가고 이유를 기록한다.
0.5~5.0점의 실제 별점은 0.5단위 그대로 저장한다. 계산용 예측값을 실제 감상 별점으로 저장하지 않는다.

## 2. 사용자 별점이 바뀌었을 때

1. Spring이 별점과 사용자 `inputVersion` 증가, 현재 추천 세트 무효화, Outbox 이벤트를 같은 DB 트랜잭션에서 저장한다.
2. Outbox 발행기가 Kafka로 변경 사실을 전송한다. Kafka 일시 장애 때문에 별점 저장 자체를 실패시키지 않는다.
3. Python 추천 Consumer가 해당 사용자의 **현재 DB 상태**를 읽는다. 이벤트의 과거 별점으로 DB 상태를 덮어쓰지 않는다.
4. 현재 평가 편수로 K를 판정하고, 최신 원본 H=10을 고른 뒤 영화 정보를 연결한다. 감상·관심없음 목록도 현재 상태를 읽는다.
5. 장르·국가·인물·대중성 등에 대한 반응과 근거 편수를 검증된 특징 생성 방식으로 다시 계산한다. GBT 모델은 그대로 사용한다.
6. 맞춤 순위와 발견용 사용자 프로필·후보를 다시 계산한다. ALS를 쓸 수 있는 부분은 Fold-in과 보조 점수를 다시 계산한다.
7. 계산 시작 때 읽은 `inputVersion`과 모델·특징·카탈로그 버전이 여전히 유효한지 검사한다. 새 입력이 생겼다면 오래된 결과를 게시하지 않는다.
8. 같은 버전 묶음의 추천 결과와 완료 표지를 원자적으로 게시한다. 게시가 끝난 뒤 Kafka 처리를 완료한다.

동일 사용자의 연속 변경은 모아서 최신 DB 상태로 한 번 계산할 수 있다. 마지막 수정 이후 10편 미만이 되면
다음 추천은 대중 추천으로 전환한다. 삭제한 별점이 사용자 특징이나 ALS Fold-in에 남아서는 안 된다.

### GBT와 ALS 보조는 무엇을 다시 계산하는가

| 항목 | 사용자 입력 변경 시 동작 |
| --- | --- |
| GBT 나무 | 그대로 둔다. 사용자 ID마다 새 모델을 만들지 않는다 |
| GBT 입력 | 영화의 고정 특징 + 사용자의 반응 + 반응의 근거량을 다시 조합한다 |
| GBT 출력 | 새 입력 특징을 같은 나무에 통과시켜 영화별 예상 선호 점수를 얻는다 |
| ALS 영화 Factor | 그대로 둔다. 현재 학습 산출물에 있는 영화만 사용한다 |
| ALS 사용자 Factor | 최신 입력 중 ALS가 아는 영화와 실제 별점으로 Fold-in한다 |
| 결합 | 후보 영화의 ALS 학습 평점 수에 따라 보조 비중을 줄인다. 입력 사용자 평가 편수 K로 이 비중을 계산하지 않는다 |

`a = 사용 가능한 ALS 점수 여부 × n_train / (n_train + 100)`  
`개인 점수 = a × 보정 ALS 점수 + (1 − a) × 보정 GBT 점수`

`n_train`은 **해당 후보 영화가 ALS 학습에서 받은 평가 수**다. 후보 Factor가 없거나 입력에 ALS 지원 영화가
없으면 `a=0`이어서 GBT를 사용한다. 보정 계수와 특징 생성 규칙도 모델 묶음에 포함해 고정한다.
점수는 순위 계산 중 연속값으로 사용한다. 현재 GBT 모델의 누락값 처리 규칙을 임의의 0점 처리로 바꾸지 않는다.

## 3. 맞춤·발견 결과를 만드는 위치

| 단계 | 맞춤 추천 | 발견 추천 |
| --- | --- | --- |
| 후보 출발점 | 서비스 전체 적격 카탈로그 | 같은 카탈로그의 고정 1,024개 하위 그룹 |
| 사용자별 선행 판단 | 현재 감상·관심없음·이미 제공한 영화 제외 | 전체 감상 이력으로 덜 본 그룹을 먼저 정하고 제외 목록 적용 |
| 빠른 후보 확보 | Consumer가 영화 특징을 나눠 읽어 전체 후보를 비동기 점수화 | 덜 본 그룹을 사용자 프로필과 비교해 순서를 정한 뒤, 그룹별 사전 대중 정렬 목록에서 최대 25편씩 확보 |
| 개인 점수 계산 | GBT + ALS shrink100 | 확보한 **최대 100편**에 GBT + ALS shrink100 |
| 결과 준비 | 점수·동률 해소 규칙에 따른 순서 보관, 다음 페이지 공급 | Top10 보관, 같은 순서에서 2편씩 공급 |
| 공급 소진 | 현재 제외 조건으로 다음 순위를 읽거나 다시 계산 | 이미 제공한 영화를 제외하고 같은 그룹 정책으로 다음 후보를 확보 |

발견의 “덜 본 그룹”은 감상 편수 2편 이하이면서 전체 매핑된 감상 영화 중 비율이 20% 이하인 그룹이다.
그룹 안에 현재 추천 가능한 미감상 영화도 있어야 한다. 그룹과 사용자의 비교에는 콘텐츠 프로필을 사용하고,
그룹 내부 사전 정렬에는 대중 지표를 사용한다. **그룹 유사도·대중 정렬·개인 예상 선호도는 각각 다른 단계다.**

최종 제외는 Spring이 응답 직전에 DB 기준으로 다시 확인한다. Consumer의 제외는 불필요한 계산과 후보 부족을
줄이는 사전 처리다. 두 검사 사이에 감상·관심없음이 추가되면 응답에서 제거하고 같은 유형의 다음 후보를 채운다.
카드 노출·관심없음·클릭을 발견 그룹의 감상 편수로 올리지 않는다. 이미 제공한 영화는 중복 방지 목록으로 따로 관리한다.

발견 후보가 부족하면 최대 2편보다 적게 제공하고 소진 여부를 알린다. 다른 그룹의 전역 인기 영화나 맞춤 영화를
발견으로 이름만 바꿔 채우지 않는다. `Top10`, B=100, 그룹당 25는 모델 학습 파라미터가 아니라 후보 공급 정책이다.

## 4. 갱신 종류와 실행 주체

| 변화 | 실행 주체와 주기 | 바뀌는 것 | 그대로 두는 것 |
| --- | --- | --- | --- |
| 별점 등록·수정·삭제 | Outbox → Kafka → Python Consumer, 이벤트 발생 시 | 사용자 특징·개인 점수·추천 결과·입력/후보 버전 | GBT 나무·ALS 영화 Factor·고정 군집 중심 |
| 확정 감상 이력 등록·삭제 | Spring inputVersion 증가·발견 버퍼 무효화 → Consumer 재계산 | 시청 제외, 덜 본 그룹의 분자·분모·발견 후보 | 별점이 함께 바뀌지 않으면 K는 그대로 |
| 관심없음·이미 노출 | Spring 즉시 제외, 다음 후보 계산에도 반영 | 제외 목록·페이지 공급 | 실제 별점·K·감상 경험량을 바꾸지 않음 |
| TMDB·KOBIS·영화 목록 | 수집/전처리 배치, **매일 06:00 KST를 운영 기본값**으로 둠 | 원천 스냅샷·영화 특징·그룹별 대중 정렬·카탈로그 버전 | GBT 모델·고정 중심·고정 기준 그룹 평균 대표·Q의 C/m |
| 앱 조회·클릭 집계 | Spark Structured Streaming | 앱 행동·전역 추세 집계 | GBT 나무, 현재 노출한 세트의 순서 |
| 모델 변경 | 새 학습 데이터·특징 변경을 검토할 때만 오프라인 실행 | 검증을 통과한 새 모델 묶음 | 이전 모델·입력·평가 증거 보존 |

06:00은 최적 주기를 증명한 실험 결과가 아니라 작업량과 최신성을 고려한 기본값이다. 이 문서는 스케줄을 생성하지 않는다.
TMDB 평점·투표 수, KOBIS 관객 수는 단위가 다르므로 하나의 원시 합계로 더하지 않는다.
KOBIS 미매칭은 관객 0명으로 저장하지 않으며, 확정되지 않은 매핑은 집계에서 구분한다.

카탈로그 배치는 수집 시각·대상 기간·ID 매핑·결측률을 기록하고 새 스냅샷 전체를 검사한 뒤 게시한다.
일부 수집이 실패하면 직전 정상 스냅샷을 유지한다. 새 영화는 고정 전처리와 중심으로 분류한다.
목록에 영화가 들어오거나 빠졌다는 이유로 군집을 다시 학습하지 않는다. 이미 있던 영화의 메타데이터 교정에 따른
재분류는 교정 이력과 함께 관리하고, 기준 자체를 바꾸는 재학습과 구분한다.

스냅샷 게시 후에는 추천 결과를 보유한 사용자의 갱신을 작업 큐에 넣어 같은 모델로 다시 예측한다.
현재 탐색 세션은 7절의 규칙을 따르고, 다음 새 탐색 세션부터 새 카탈로그 결과를 사용한다.
결과가 없는 사용자는 다음 요청에서 계산을 준비한다. 실제 API 요청이 전체 카탈로그 추론을 동기로 기다리도록 만들지 않는다.

**KOBIS 정보를 기존 GBT 특징에 임의로 추가할 수는 없다.** 현재 모델이 학습하지 않은 새 특징은 새로운
`featureVersion`과 오프라인 학습·평가가 필요하다. KOBIS를 후보 확보/대중 정렬에 사용하는 정책 변경과 구분한다.
한국 제작이라는 이유만으로 예측 별점에 고정 가산점을 더하는 것도 이 운영안의 규칙이 아니다.
외부 대중 점수식은 별도 데이터 비교·정렬 정책에 따르며, 변경하면 `policyVersion`을 갱신한다.

이번 로컬 후보 정책은 [상세 정책](POLICY-DETAILS.md#6-대중-목록과-kobis-후보-결합)의 그룹별
Q20+KOBIS5, 합계 최대25편이다. 과거 K128의 Q25 실험과 구분한다. Q의 C/m과 기준 그룹
평균 대표는 일별 갱신 때 다시 학습하거나 재산출하지 않는다.

## 5. 한 달 프로젝트에서 모델은 어떻게 관리하는가

서비스 실행 중에는 검증한 `GBT120_s339`, ALS 보조 산출물, 보정 계수, 특징 생성 규칙을 한 묶음으로 고정한다.
신규 사용자의 소량 평가가 들어왔다는 이유로 매일 전체 모델을 재학습하지 않는다. 사용자 반응은 2절의 재예측으로 반영한다.

새 모델이 필요한 경우에만 다음 절차를 따른다.

1. 새 학습 데이터 또는 바뀐 특징의 범위와 시점을 고정한다. 같은 사용자의 평가 목표가 입력 특징에 섞이지 않게 한다.
2. 기존 모델과 동일한 비교 조건에서 학습·검증·평가한다. MSE, Top2/추가 2편, 저평점 노출, 신규 영화 지원, 비용을 함께 본다.
3. 이전 버전을 덮어쓰지 않고 새 모델·전처리·특징 순서·보정 계수·출처를 저장한다.
4. Consumer에서 오프라인 예측과 동일한 값이 나오는지 확인하고, 별도 버전의 추천 결과를 준비한다.
5. 버전 정합성 및 오류 검사를 통과한 결과만 활성화한다. 실패하면 직전 정상 버전을 유지한다.

Spark에서 학습한 GBT를 Python Consumer에 연결할 때는 검증한 서빙 변환/추론 방식과 특징 순서를 같이 전달한다.
Spark 모델 파일 경로만 넘기면 Python에서 자동으로 같은 추론을 수행할 수 있다고 가정하지 않는다.
ALS가 재학습되면 영화 Factor가 달라지므로 사용자 Fold-in과 결합 점수도 다시 만들어야 한다.

## 6. 책임과 장애 처리

| 구성 요소 | 책임 | 장애·재시도 기준 |
| --- | --- | --- |
| PostgreSQL / Spring | 실제 평점·감상·관심없음의 원본, 입력 버전, 추천 세트·노출 이력 | 도메인 변경과 Outbox 저장을 함께 커밋한다 |
| Outbox 발행기 | 저장한 이벤트 JSON과 같은 eventId를 Kafka에 전달 | 실패를 PENDING으로 남겨 재시도. 발행 후 DB 완료 갱신이 실패하면 중복 발행 가능 |
| Kafka | 사용자 변경을 추천 Consumer에 전달 | 같은 사용자 파티션을 사용하되 도착 순서가 실제 입력 순서라고 가정하지 않는다 |
| Python 추천 Consumer | 최신 DB 재조회, 특징·추천 결과 계산, 버전 묶음 게시 | 사용자별 중복 계산을 합칠 수 있고 오래된 작업의 게시를 거부한다 |
| Redis | 완성된 버전의 추천 결과 전달 | 부분 결과를 활성화하지 않는다. 장애 시 이미 저장된 세트도 최신 제외·입력 버전을 만족하는 경우만 사용 |
| Spring 추천 API | 버전 확인, 최신 제외, 유형별 최대 2편 제공, 노출 이력 | 입력이 바뀐 이전 세트를 계속 제공하지 않는다. 후보 소진과 계산 대기를 구분 |
| Spark Batch | 원천 정제·영화 특징·그룹 정렬 스냅샷, 필요한 오프라인 학습 | 완료된 새 스냅샷만 게시, 실패 시 이전 정상본 유지 |
| Spark Streaming | 여러 사용자 행동·인기 집계 | eventId 중복 제거와 이벤트 시간 처리. 개인 GBT 추론과 분리 |

강한 신호의 멱등성은 최신 DB 상태에서 재계산하는 데서 얻는다. 버전 증가·게시 자체도 중복에 안전하게 구현해야 한다.
Kafka offset은 해당 결과를 성공적으로 게시한 뒤 커밋하며, 병렬 처리한다면 **해당 파티션에서 연속으로 완료된
구간까지만** 커밋한다. 뒤 이벤트만 완료됐다고 앞 미완료 이벤트를 넘어가면 안 된다.
실패 결과를 성공으로 표시하거나 부분적으로 쓴 Redis 키를 읽어 추천을 만들지 않는다.

## 7. 버전과 2편씩 페이지 제공

다음은 **새 로컬 설계의 논리적 버전 묶음**이다. 기존 팀 계약에 아래 필드가 모두 존재한다는 뜻이 아니다.

| 식별자 | 언제 바뀌는가 |
| --- | --- |
| `modelVersion` | GBT·ALS·보정 계수 등 모델 묶음이 교체될 때 |
| `featureVersion` | 특징의 의미·순서·전처리·누락값 처리 방식이 바뀔 때 |
| `catalogVersion` | 영화 정보·적격 목록·외부 대중 정렬 스냅샷이 바뀔 때 |
| `policyVersion` | K, 후보 확보, 발견 판정, 대중 정렬식 등 정책이 바뀔 때 |
| `inputVersion` | 별점·온보딩·필터 또는 확정 감상 이력이 바뀔 때. Spring/DB가 소유 |
| `candidateVersion` | 사용자 추천 결과를 새로 게시할 때. 기존 값에서 단조 증가 |
| 추천 세트 ID / 페이지 번호 | 특정 버전 묶음과 유형의 추천 순서에서 어느 2편을 제공했는지 식별 |

`modelVersion`만 같다고 최신 추천이 아니다. 같은 사용자에서 두 작업이 겹치면 최신 `inputVersion`과
선택한 모델/카탈로그 묶음에 맞는 결과만 게시한다. Redis 키를 따로 읽더라도 완료된 동일 묶음인지 확인해야 한다.

| 요청·상황 | 페이지 처리 |
| --- | --- |
| 첫 요청 | 현재 입력 버전의 맞춤 세트를 만들어 최대 2편 반환 |
| 발견 요청 | 발견 유형의 별도 순서에서 최대2편 반환. K 미충족 또는 GBT 입력 불가이면 초기 추천으로 유형을 명시해 반환. GBT 가능·콘텐츠 방향 불가이면 맞춤만 개인 예측을 유지하고 발견은 초기 추천 |
| 다음 2편 | 기존 세트의 다음 미노출 순서 사용. 현재 DB 제외 조건은 다시 검사 |
| 같은 페이지 요청 재시도 | 같은 request/page 할당을 재사용하고 커서를 두 번 전진시키지 않음. 최신 강제 제외를 우선하며 같은 페이지 교체 revision을 저장·재사용 |
| 같은 사용자 동시 요청 | 페이지 할당과 노출 기록을 하나의 DB 트랜잭션/잠금으로 처리해 동일 영화 중복 소비 방지 |
| 별점 변경과 페이지 요청이 겹침 | 페이지 할당 시 inputVersion 재검사. 바뀌었으면 이전 세트를 무효화하고 새 계산 결과를 기다림 |
| 관심없음 | 같은 유형의 다음 후보로 교체. inputVersion·실제 별점·K는 유지 |
| Top10 또는 현재 공급 소진 | 제공한 영화는 제외한 뒤 다음 후보 확보. 발견 조건을 풀어서 자동 채우지 않음 |
| 카탈로그·모델 갱신 | 현재 탐색 세션의 버전은 유지하되 삭제·부적격 영화는 즉시 제외. 다음 새 탐색 세션부터 새 스냅샷 사용 |

세션은 한 번의 연속 탐색이며 그 안의 Top10 버퍼/세트와 다르다. 다음 버퍼를 채워도
일반 모델·카탈로그 버전은 바꾸지 않는다. 사용자 입력 변경은 즉시 이전 버퍼를 무효화하지만
해당 탐색의 공통 노출 집합을 보존한다. 확정 감상이 늘거나 줄면 그룹 경험량도 다시 계산한다.
발견은 각 Top10 버퍼 안에서 개인 점수순이며 세션 전체의 점수 단조 감소를 보장하지 않는다.

대중 추천으로 돌아갈 수 있는 경우는 저이력, 개인 특징 생성 불가, 개인 모델 계산 실패 등으로 명시하고
응답의 추천 방식/사유를 기록한다. **개인화 결과라고 표시한 채 인기 순위를 반환하지 않는다.**
발견 실패는 발견 준비/후보 부족 상태로 알린다. 외부 인기 스냅샷까지 없거나 안전하게 제공할 결과가 없으면
추천만 일시 이용 불가로 처리하고 영화 조회·별점 저장은 유지한다.
