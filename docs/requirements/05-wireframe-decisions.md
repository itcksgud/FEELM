### 3.1 1·2차 누적 기준에서 8번의 의미

1·2차 누적 기준에서는 현재 추천 3개를 새로고침으로 교체할지, 페이지네이션으로 이어 붙일지를 정하지 않았다. 3차 결정에서 **Rating 등 추천 입력이 바뀌지 않으면 기본 추천 3개를 유지**하기로 했으므로 단순 재조회용 페이지네이션·새로고침 정책은 더 이상 필요하지 않다.

### 4.1 AR-02의 계정 관계

- 소셜 회원가입: `Google 계정 A → FEELM User 1`을 새로 만든다. 이 관계는 1:1 제약을 위반하지 않는다.
- 같은 Google 계정 A를 다른 FEELM User에 다시 연결할 수 없다.
- 한 FEELM User는 이메일 로그인과 Google·Kakao·Naver 식별자를 각각 연결할 수 있다. 따라서 전체 구조는 `User 1 : 로그인 수단 N`이지만, **각 소셜 식별자는 User 하나에만 속한다**.
- 기존 계정으로 로그인한다는 것은 비밀번호 또는 이미 연결된 다른 로그인 수단으로 본인 계정에 로그인하는 것이다. 로그인 후 설정에서 새 소셜 제공자를 연결한다.

## 5. 최신 용어 및 구현 원칙

- 감상 확인 후 평가 전 상태는 사용자에게 `감상 완료 · 평가 대기`, 내부에서는 `WATCHED_UNRATED`로 표현한다.
- 최초 Rating 저장 후 상태는 `RATED`이며, 이때 Frame·Popcorn을 생성한다.
- Rating을 삭제하면 해당 평가로 생성된 Frame·Popcorn도 삭제하고 취향 집계에서 제거한다. 감상 이력은 `WATCHED_UNRATED`로 유지한다.
- 감상 이력이 있는 영화는 Rating을 삭제해도 개인·발견 추천 후보에서 제외한다.
- 온보딩의 좋아요/싫어요는 일반 Rating에 저장하지 않는다.
- 온보딩 미선택은 저장하지 않는 건너뛰기이며 즉시 새 후보를 제시한다.
- 필름은 전체 프레임 모음이다.
- 리포트는 반기 단위다.
- 리포트 공유 링크는 서버에 저장하고 생성 후 1개월 뒤 만료하며, 외부 사용자가 접근할 수 있다.
- 저장·공유 리포트는 PNG로 생성하고 비공개 S3 호환 객체 스토리지에 저장한다. PDF는 현재 범위에서 제외한다.
- 객체 스토리지는 MinIO에 종속시키지 않고 S3 호환 인터페이스로 추상화한다. 로컬·자체 운영은 MinIO, 관리형 클라우드는 해당 클라우드 객체 스토리지를 기본 선택으로 한다.
- `Party`를 사용하고 `Group`과 혼용하지 않는다.
- 파티는 최대 4명이며 앱 안에서 닉네임으로 초대하고 수락한다.
- 현재 추천 composition은 BASELINE_THREE이며 discovery 2+1은 새 evidence·제품 결정 전 표시하지 않는다.
- 최초 3편 뒤 요청마다 최대 3편을 기존 collection 뒤에 누적한다.
- 구독하지 않은 OTT의 영화도 추천 후보에서 제외하지 않는다.
- 팝콘 맛은 8개로 구성하되 명칭과 매핑은 데이터 분석 후 확정한다.
- 소셜 로그인은 구글·카카오·네이버를 지원한다.
- 평가 제출 완료 또는 명시적 `관심없음`이면 해당 추천을 목록·향후 후보에서 제외한다. 감상만 완료한 경우는 유지한다.
- 취향 리포트의 상세 구성은 아직 미정이다.

## 6. 저장 방식 선택 근거

- PNG 같은 바이너리 파일은 서비스 DB보다 객체 스토리지에 두고, DB에는 파일 메타데이터와 권한 상태를 둔다.
- MinIO는 S3 API를 제공하므로 애플리케이션이 S3 호환 인터페이스만 사용하면 운영 환경에 따라 MinIO 또는 관리형 S3 계열 저장소로 교체하기 쉽다.
- 객체는 기본 비공개로 두고, 사용자가 다운로드할 때만 짧은 만료의 URL을 발급한다. 리포트 공유 토큰의 1개월 유효기간과 실제 파일 다운로드 URL의 짧은 유효기간은 서로 다른 정책이다.

참고: [MinIO AIStor S3 API 안내](https://docs.min.io/aistor/developers/), [Amazon S3 presigned URL 안내](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
